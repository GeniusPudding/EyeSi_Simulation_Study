## 1. 機制:三件事

一句話:**彈性薄膜 + 沿網格邊的離散裂縫,用主應力門檻觸發、沿 ⊥σ₁ 前進**。

### (a) 力學(純彈性)
- `TriangularFEMForceField method="large"`(線性共旋膜)+ `MeshSpringForceField`(每條邊一個線彈簧,抗伸長)
  + `TriangularBendingSprings`(抗彎)+ `DiagonalMass` + `UniformVelocityDampingForceField`。
- 幾何來自 [`generate_cap.py`](../../Capsulorhexis/scenes/generate_cap.py) 的扁橢球(oblate,A=7、C=1.5),
  囊膜是貼合其上緣的圓弧片;`EllipsoidForceField` 當水晶體的**解析障礙**(正剛度=向外推),外緣以
  `FixedProjectiveConstraint` 固定(懸韌帶錨,anatomical zonule)。
- **關鍵性質:純彈性**——放手就彈回原狀(§5 會說明這是最大的限制根源)。

### (b) 裂縫幾何:runtime 頂點分裂
裂縫是一條頂點路徑 `self.crack = [..., prev, tip]`,只有 `tip` 還連著。前進 = 把 `tip` 的三角形扇面
沿兩條裂邊(往 `prev`、往選定的 `next`)剖成兩片唇,一片保留原頂點、另一片改接一個**預留備用頂點**
(`_split_tip`,`cap_tear.py`)。備用點池在建網格時就配好(park 在網格內,避免撐大 bbox);分裂後
`fem/springs/mass.reinit()` 讓力學元件吃到新拓樸,並把新三角形清單**推給 OglModel**(否則畫面那層皮
不會跟著開)。

> 裂縫**只能沿現有網格邊**一格一格走 —— 這是與 INRIA「沿任意路徑重網格」最本質的差別(§5.2)。

### (c) 判據:σ₁ 門檻 + ⊥σ₁ 方向(Rankine)
每 `TEAR_CHECK_DT` 檢查一次(`onAnimateBeginEvent` / `_advance_once`):

```
每個三角形:F = Ds·Dm⁻¹              (Dm=靜止邊框, Ds=當前邊框, 逐三角形防呆 2×2 逆)
           ε = ½(FᵀF − I)          (Green 應變, 平面)
           σ = C:ε                 (平面應力, C = E/(1−ν²) 的各向同性矩陣)
           σ₁ = ½(σxx+σyy) + √(((σxx−σyy)/2)² + σxy²)   (主應力)
裂尖判定:  khot = argmax σ₁ (碰到 tip 的三角形中最燙的那個)
           若 σ₁(khot)·TIP_STRESS_GAIN < STRESS_THRESHOLD → 不前進(只是繃緊)
           否則 perp = normalize(n × σ₁方向)             (⊥σ₁, 落在裂尖切平面內)
                next = 與 perp 最對齊、且在環帶內的鄰居頂點(強制往前)
                _split_tip(tip, prev, next)
```

- **σ₁ 由幾何(靜止 vs 當前)算出**,與哪個元件在施力無關 → 判據不綁定特定力學模型。
- **⊥σ₁ 用裂尖的局部法線 `n`**(非寫死 z 軸),裂縫才會貼著彎曲的膜面走。
- **路徑不寫死**:同一條規則,平片均勻拉 → 直線;彎膜放射狀拉 → σ₁ 指向半徑 → ⊥σ₁ 是圓周 → **裂縫自然彎成圓**。

#### ⚠️ 已修正的 bug:主應力**方向**曾有一半是錯的(2026-07-23)

`cap_membrane.py` 的 `principal_stress()` 原本這樣算主應力方向:

```python
ang = 0.5 * np.arctan2(2*σxy, np.maximum(σxx − σyy, 1e-12))   # ← 錯
                               ~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

`arctan2(y, x)` **靠 x 的正負號決定象限**。那個 `np.maximum(..., 1e-12)` 把分母**強制變正**,正好抹掉它唯一需要的資訊 —— 凡是 **σyy > σxx**(分母本該為負)的狀態,象限全錯。

而且該保護**根本不必要**:`arctan2` 是雙參數函式、**不做除法**,`x=0`(甚至 `x=y=0`)它自己就處理得正確。

**對照解析解的實測**:

| 應力狀態 | 解析解 | 正確式 | 舊程式碼 | 誤差 |
|---|---|---|---|---|
| 單軸拉伸沿 x | 0° | 0° | 0° | ✅ |
| **單軸拉伸沿 y** | 90° | 90° | **0°** | **90°** |
| 純剪切 | 45° | 45° | 45° | ✅ |
| σxx=0, σyy=2, σxy=1 | 67.5° | 67.5° | **45°** | **22.5°** |

端到端驗證(檢查「沿回傳方向的正向應力是否等於 σ₁」,20000 個隨機應力狀態):
**修正前 9990/20000 = 50.0% 錯誤;修正後 0/20000。** 隨機狀態恰有一半滿足 σxx < σyy,全數受害。

**為何這件事很嚴重**:Rankine 準則是「裂縫**垂直於** σ₁」。方向錯 90° → 裂縫方向**完全相反** → log 裡的
`crack CIRCUMFERENTIAL (good, curvilinear)` 與 `crack RADIAL (runs to the periphery!)` **會互換**。
那正是撕囊訓練最關心的指標(Argentinian-flag 逃逸),也是 `Capsulorhexis` plugin 的 argmax-c 準則
將來要吃的輸入 —— **用錯誤的方向做撕裂決策,會系統性地誤判**。

**修正**:移除該保護,`ang = 0.5 * np.arctan2(2*σxy, σxx − σyy)`。

**影響範圍**:此角度**只用於診斷輸出**(`sigma1_vs_radial` 分類、應力著色),**不回饋到力的計算**,
所以修正不改變任何動力學/手感;σ₁ 的**大小**(`½(σxx+σyy) + √(…)`)一直是正確的,錯的只有**方向**。

> **教訓**:對「除以零」的反射式防護,套在 `arctan2` 這種**不做除法**的函式上,會把正確性一起防掉。
> 診斷指標本身出錯最危險 —— 它不會讓模擬崩潰,只會讓你**根據錯的數字做判斷**。

## 2. 工程細節(得來不易的穩定性與收尾)

這些不是論文機制,是把上面三件事做成「不會崩、看得到」的必要防護,列成表備查(皆在 `cap_tear.py`):

| 機制 | 參數 | 為什麼 |
|---|---|---|
| **環帶約束** | `TEAR_R_MIN=3.0`、`TEAR_R_MAX=6.0` | 裂縫若捲進中央**極點**(自適應環收斂的奇異點),分裂會生退化細三角形 → FEM `Null determinant` → inf 爆掉。限制在 r∈[3,6] 環帶內;撕囊本來就是 r≈5 的環,路徑仍在環內自由湧現。 |
| **面積夾限** | `AREA_MIN_FRAC=0.30` | 三角形被拉到面積<30% 靜止面積(純剪切/翻面,邊長夾限抓不到)→ FEM 除以零。把過小三角形繞質心撐回去。實測:9000 力的暴力猛拉仍維持有限值。 |
| **回滾安全網** | `last_good_pos` | FEM 內部若仍炸出 inf(在夾限之前),下一步偵測到非有限值就**回滾上一個好狀態、速度歸零**。場景**再也不會永久消失**。 |
| **速度/應變夾限** | `MAX_SPEED=25`、`MAX_STRETCH=1.5` | 猛拉的大衝量、邊不得超過 1.5× 靜止長。 |
| **滑鼠力上限** | `MOUSE_STIFFNESS=250`(低) | 附著彈簧力 = 剛度 × 拖曳距離,**無上限**;高剛度把游標拖出畫面 = 巨大衝量 → 塌陷。壓低剛度封住遠拖的力。 |
| **裂尖應力集中** | `TIP_STRESS_GAIN=2.0` | 真實裂尖有應力奇異點,粗網格會低估 → 乘一個集中係數,手拉才拉得動(§5.3)。 |
| **起始缺口(穿囊針)** | `PRE_TEAR_DEG=100` | 開場沿圓周幾何預撕約 100°,給一片可抓的瓣(對應臨床:穿囊針先刺切口)。內部種子(非外緣),否則裂尖被固定住、σ₁ 到不了門檻(§5.3)。 |
| **圓片掀起** | `LIFT_AFTER_CRACKLEN=75`、`DISC_LIFT_Z=14` | 撕過 ~3/4 圈後,開向上浮力(泡在玻璃體中)把已近乎切下的中央圓片掀起、露出圓洞。**只在大撕之後才啟動**,不會一開始自撕。 |

## 3. 實測:做得到什麼(皆有數據)

- **裂縫從應力場湧現、彎成圓**:彎膜放射狀加載下,裂尖半徑維持 r≈5.4–6.4,角度單調掃過
  176°→−31°(約 **207° 圓弧**),裂口開到 ~0.9。沒有任何程式碼畫圓。
- **同規則、換加載 → 換路徑**:對稱加載裂縫半徑 spread=0.4(圓);不對稱(往側邊拉)spread=3.6(跟著拉走)。
  證明「固定半徑」是加載對稱性的結果,不是寫死。
- **一次撕一段**:`MAX_ADVANCE_PER_CHECK=6`,拉力夠時一次前進多格,像「撕」而非一格一格跳。
- **圓片掀起露洞**:撕過 75 格後浮力把圓片從 z=1.5 掀到 **z=7.5**,呈現「撕囊完成、露出圓洞」。
- **不會崩**:暴力猛拉(9000 力)全程維持有限值(面積夾限 + 回滾)。

## 4. 診斷工具:`[Pull]` log

`onAnimateBeginEvent` 內建拉動診斷,拉的時候印出:裂尖 σ₁(判據實際看的值)、全場最大 σ₁ 在哪、
你拉的點在哪 + **離裂尖多遠**。這條 log 直接揭示了核心難點(見 §5.3):

```
[Pull] tipSigma1=10 (x2.0=20 vs thr 10) tip@r5.1,-37d | maxSigma1=137@r4.2,-11d | youPull@r4.1,-17d dist-to-tip=1.9
```
你拉的地方 σ₁=137,但傳到 1.9 之外的裂尖只剩 10 —— **判據沒錯,是力傳不到裂尖**。

### 4.1 `cap_membrane.py` 的即時應力觀測器 + 熱圖

`cap_membrane.py` 的 `principal_stress()` 是一個**幾何觀測器**:每 `STRESS_EVERY` 步,從
靜止 vs 當前幾何算 F → Green 應變 ε = ½(FᵀF−I) → 平面應力 σ = C(E,ν):ε → σ₁ 與方向。
它**只讀不施力**,和用 FEM 或 mass-spring 無關(ε 純幾何)。

**觀測器 = FEM 真實應力(小應變下)**:FEM 內部也是用同一個 F、同一條 σ=C:ε 產生力,唯一
自由參數是 E、ν。所以 `_stress_material()` 讓觀測器在 FEM 模式**直接讀 FEM 的 live
`youngModulus`/`poissonRatio`**(會跟著 cloth→paper 在 SWITCH_T 的 ramp 走),回報的 σ₁
就等於 FEM 實際施力用的應力(小應變精確;大應變因觀測器用 Green、FEM 用共旋線性而略有差異)。
mass-spring 模式沒有連續體 E,退回固定 `STRESS_E/STRESS_NU` —— 此時數值只是**幾何應變比例尺**,
但「哪裡受力最大」的空間分佈兩個模式一致。

**與 SOFA 原生 FEM 應力的交叉驗證**(可重現:[`verify_stress.py`](../../Capsulorhexis/scenes/verify_stress.py),
`py -3.12 scenes/verify_stress.py`)。SOFA 的 `TriangularFEMForceFieldOptim` 有自己的主應力
(`computePrincipalStress` + `showStressVector`,`CAP_FEM_STRESS_VIZ=1`),但 `triangleInfo` 在
Python 讀不到("Invalid type")、`stressMaxValue` 只在繪圖時算,所以無法即時逐值比對。改以 numpy
**重實作 SOFA 的公式**(共旋**線性**應變 ε_L = U−I,U = √(FᵀF))和我們的 Green 版逐格比對,結果:

| 均勻拉伸 | 方向差(中位/最大) | σ₁ 比值 corot/green(中位) |
|---|---|---|
| 2% | 0.000° / 0.000° | 0.990 |
| 10% | 0.000° / 0.000° | 0.953 |
| 20% | 0.000° / 0.000° | 0.910 |
| 50% | 0.000° / 0.000° | 0.802 |

- **方向恆等**(0.000°,任意應變):ε_G、ε_L 都與伸張張量 U 同軸,主方向必然相同 → SOFA 的
  `showStressVector` 方向線與瀏覽器白線指同方向。
- **大小**:小應變幾乎相同,大應變我們(Green)略大(`½(U²−I) > U−I`),50% 拉伸時 SOFA≈我們的 80%。
- 對照解析解:單軸 λ=1.2,解析 σ₁=290.1 = 我們 290.1、方向 0° → **觀測器數值可證為正確**。
- `verify_stress.py` 內建 self-check:其 inline Green 與**出貨版 `principal_stress()` 逐格差 <1e-12**,
  確保驗的是真正跑的函式。

**即時力場 UI(解耦式)**(`CAP_HEATMAP=1` / `run_cap.ps1 -Heatmap` / `run_cap.sh --heatmap`):
SOFA 的**變形視窗完全不動**,另外把 σ₁ 場透過一個**極簡本機 HTTP 服務**(Python 標準庫、背景
執行緒)推出去;一個自足的瀏覽器頁面 [`stress_viewer.html`](../../Capsulorhexis/scenes/stress_viewer.html)
輪詢它,畫出**未變形參考圓盤**(= 變形膜的一張材料空間「地圖」)的即時熱圖,支援 **hover 浮現數值**
(σ₁ / 裂縫方向 / 裂向分類)、**時間軸回放**、色階條、說明面板(`?`)。

- **資料流**:controller 每 `STRESS_EVERY` 步把一幀(σ₁ / 裂縫角 ang / area_ratio,逐三角形)
  序列化成 JSON 字串。背景 HTTP 服務五個路由 —— `/`(頁面)、`/geometry`(靜態參考圓盤,只取一次)、
  `/stress`(最新幀,即時輪詢)、`/meta`(緩衝幀範圍)、`/frame?i=N`(第 N 幀,供拖桿回放)。
  字串換參考/append 都在 GIL 下原子完成,server 執行緒讀取無鎖;兩邊各有事件迴圈,互不阻塞。
- **錄製 + 回放(解單螢幕痛點)**:每幀同時 (a) 進一個**上限環形緩衝**(`CAP_STRESS_HISTORY`,
  預設 1500 幀)供頁面**時間軸拖桿/播放**即時回看,(b) append 到 **`scenes/stress_log.jsonl`**
  (每行一幀完整場,已 gitignore)供離線分析。所以**可以先自由拉、不用盯著看,事後再拖回任一時刻
  hover 查數值** —— 不必為了定格而放開滑鼠。空白鍵在 LIVE / 回放間切換。
- **為何放在 SofaImGui 之外**:SofaImGui **無法讓場景注入自訂 widget**,所以 hover-tooltip
  在 SOFA GUI 內做不到;把力場畫在**我們自己的頁面**裡,hover/數值/回放就全部可行。這也符合
  本 repo 既有的 `docs/demo_*.html` canvas demo 慣例。
- **效能 / 穩定性連動**:每幀序列化 4166×3 值原本用 per-element Python 迴圈,**把 FPS 砍半**
  (163→64);而 FPS 一低,即時滑鼠目標在兩步間跑得更遠 → `DISP_CLAMP` 飽和 → **整片彈開**,
  所以這個序列化成本本身就是「扭曲彈開」不穩的來源之一,不只是延遲。修法:(a) numpy 向量化
  `np.round(...).tolist()`(64→99);(b) `STRESS_EVERY` 預設 3→**6**(場更新頻率 ~8 Hz,足夠)
  → **143 FPS(僅比關閉低 ~12%)**。背景執行緒**無效**(GIL 會把它與物理執行緒序列化,實測無改善)。
  拉動仍覺重就把 `CAP_STRESS_EVERY` 調更大。
- **裂向分類**:頁面端重現終端機邏輯 —— 裂縫 ⊥ σ₁(Rankine),量 σ₁ 方向與**徑向**的夾角:
  <30° → 裂縫 CIRCUMFERENTIAL(good);>60° → RADIAL(runs to periphery);之間 → oblique。
  退化三角形(area ratio 超出 `DEGEN_LO..DEGEN_HI`)標灰、σ₁ 非物理。
- **色階用 p98,不用 max**:滑鼠拉點附近少數「近退化但仍合法」(area ratio 逼近 4.0)的三角形
  σ₁ 可達整體 ~100 倍(實測某次拉動峰值 32370,主體僅數百),用 max 當色階上限會把整張圖壓成藍。
  故自動色階取**載荷格的第 98 百分位**(frame 的 `sp98`),峰值仍以飽和紅呈現、但主體分佈看得出來;
  HUD 同時顯示 `peak`(max)與 `p98`。`Scale` 鈕可切固定上限 `STRESS_HEAT_MAX`。
- **預切圈預設關閉**:`generate_cap.py` 的 `TEAR_ENABLE` 改為 env 控制、預設 off(`CAP_PRESLIT=1`
  才開)。它的重合雙頂點環會在膜上呈現一條 seam、並在熱圖 r≈`TEAR_RADIUS` 產生假應力環;做 scripted
  tear 那一階再開。
- **錄製檔保護**:每次啟動會先把上一份 `stress_log.jsonl` 更名為 `.prev`,重跑不會靜默毀掉想分析的紀錄。
- **log 格式**(`stress_log.jsonl`,每行一 JSON):`{i, step, t, s1[Ntri], s2[Ntri], ang[Ntri], aratio[Ntri],
  smax, heatmax}`;三角形拓樸與參考座標見 `/geometry`(或 `cap.obj`)。numpy 逐行 `json.loads` 即可分析。

### 4.2 INRIA argmax-c 判據:即時試算(瀏覽器)+ 數值驗證

在熱圖頁的撕裂門檻面板加了 **criterion 切換**:`Rankine ⊥σ₁`(各向同性)↔ **`INRIA argmax-c`**
(纖維各向異性,Dequidt 2013 Eq.1–4 的**成核形式**,H=1)。實作(`stress_viewer.html` 的
`inriaC()`;numpy 參考實作 + 驗證在 [`verify_stress.py`](../../Capsulorhexis/scenes/verify_stress.py)
的 `inria_c()`):

```
對每個元素、每個候選裂向 d(0–180°,5° 步):
  u = d + 90°                        (開裂法向:垂直裂縫、把裂縫「拉開」的方向)
  σ_u = σ₁·cos²ψ + σ₂·sin²ψ         (Eq.3 改寫到主軸座標;ψ = u 與 σ₁ 方向的夾角)
  σ̄_u = σ̄_T + (σ̄_L−σ̄_T)·(1 − fold(u,f)/90°)^α     (Eq.4;f = 纖維方向)
  c(d) = σ_u / σ̄_u                   (σ_u ≤ 0 壓應力不開裂 → c=0)
撕裂 ⟺ max_d c ≥ 1;裂向 = argmax_d c              (Eq.1–2,成核 H=1)
```

- **σ₂ 需要新增**:重建任意方向的 σ_u 需要**兩個**主值。觀測器本來就算了(`mid−dev`),
  現在 `principal_stress()` 回傳 4-tuple、frame/log 多 `s2` 欄。
- **纖維場 f 解析可得**:囊膜纖維是**同心圓**(Dequidt:每 0.5mm 一圈)→ 每個元素的 f =
  質心方位角 + 90°(切線),`loadGeometry` 時預算。
- **能即時算**:c ≤ σ₁/σ̄_T(σ_u≤σ₁、σ̄_u≥σ̄_T),所以只有 σ₁ ≥ σ̄_T 的元素可能撕 →
  先用這個上界過濾,36 方向搜尋只跑熱區,60fps 無壓力。
- **驗證**(`py -3.12 scenes/verify_stress.py`):
  1. **各向同性特例 = Rankine**(論文明述的等價):σ̄_L=σ̄_T 時,5000 隨機應力態的 argmax
     裂向與 ⊥σ₁ 差 ≤ 搜尋步長、c 與 σ₁/σ̄_T 差在**離散化理論上界**(6.1e-4)內 → OK。
  2. **跨纖維抑制**:單軸拉伸沿纖維(Rankine 裂向的 u ∥ f)→ σ̄_L/σ̄_T=4 時 c 從 5.0 壓到
     1.61,argmax 裂向從 90° 轉向 61°(被纖維帶偏)。
  3. **同心纖維 → 圓周撕**:σ₁ 徑向 + 纖維切向(囊膜情境)→ 200 個元素 argmax 裂向與纖維
     夾角 ≤0.5° → **裂縫沿圓周 = CCC 維持圓弧的機制**,數值重現。

**參數可得性(「還缺什麼拿不到」的正面回答)**:

| 公式需要 | 來源 | 狀態 |
|---|---|---|
| σ 張量(σ₁、σ₂、θ₁) | 幾何觀測器 | ✅(本次補 σ₂) |
| 纖維方向 f | 同心圓解析(切線) | ✅ 幾何導出 |
| **σ̄_T、σ̄_L、α** | **論文未給數值**(原文:門檻依外科醫師回饋調出) | ❌ **不可得 → 滑桿即時調** |
| p、θ_P(Eq.2 的 H 項) | 需要**裂尖追蹤**(上一步裂向) | 下一階段(成核先 H=1) |
| 裂尖鄰域加權應力 | 需要裂尖位置 | 下一階段 |

> [補充] 單位也是「拿不到」的一部分:模擬應力是 sim-unit(E=1200 非 Pa),文獻的囊膜強度
> (MPa 級)無法直接代入 —— 調參是誠實做法,與論文相同。`stress_log.jsonl` 已含 `s2`,
> 離線可對任何錄製重算 c 場。

### 4.3 σ̄_T 實測校準:門檻越低**不是**越好裂(非單調)

上表說 σ̄_T「論文未給 → 只能調」,那就用同一段固定的溫和拉動(`probe_gentle.py`,腳本化位移,
排除手感差異)把它掃出來。**[實測]**,非論文內容:

| σ̄_T | 裂縫頂點 | 退化元素 | 仍黏附 | 說明 |
|---|---|---|---|---|
| 600 | 25 | 0.1% | 2132 | 幾乎撕不動 |
| **220** | 179 | 0.0% | 2050 | 可控的短裂 |
| **20**(現行預設) | **563** | 0.1% | 1682 | 長而順、網格健康 |
| 1(最低) | **204** ⬇ | **24.8%** 💥 | 39 💥 | **反而更短**,網格碎掉 |

**關鍵觀察:σ̄_T 從 20 降到 1,裂縫不是變長而是變短(563 → 204)。** 這個非單調性揭露一個
本 demo 特有的**自毀迴圈**:

```
門檻過低 → 單步撕過多 → 三角形塌陷成退化元素(area_ratio 落在 0.25..4.0 之外)
         → 退化元素的 σ₁ 是數值垃圾(塌陷三角形算出上萬的假應力)
         → 假應力餵回判據,c 更大 → 撕得更兇 …(正回饋)
         → 最後裂尖鄰域全是退化元素 → 判據拿不到有效應力 → 撕裂**卡死**
```

也就是說:**撕裂與應力場經由「網格品質」互相耦合**,不是兩個獨立模組。這回答了
「到底是撕裂演算法問題還是應力計算問題」——**兩者都沒壞**:σ̄_T=20 時演算法撕出 563 個
頂點、退化率 0.1%,應力場乾淨;問題只在撕裂速率超過網格能承受的重整速度時才出現。

**對策(`CAP_TEAR_DEGEN_MAX`,預設 0.04)**:每次撕裂機會先量退化元素比例,超過上限就
**暫停撕裂**讓膜鬆弛,網格恢復後自動續撕。這只是安全網 —— σ̄_T=20 時退化率 0.1%,煞車
從不觸發、行為完全不變;σ̄_T=1 時它把退化率從 24.8% 壓到 5.6%、最大座標從 8.34 收回 6.53。
它**不能**讓一個荒謬的門檻變得合理,只是避免整個網格被撕爛。

> [補充] 這是本 demo 的**離散化假象**,不是 INRIA 方法的缺陷。論文用**沿裂縫路徑重網格**
> (§5.2、[`ccc_method/2`](../ccc_method/2_topological_remesh.md))在撕裂當下就維持元素品質,
> 從源頭避免退化;本 demo 只沿現有邊裂、不重網格,才需要這道煞車。

### 4.4 「拉不動」的真正原因:力傳不到裂尖的核函數(不是門檻,也不是應力)

σ̄_T 調到 20 之後仍然「要非常用力才長出一點點裂痕」。用**忠實複製滑鼠的 probe** 量出來
(`AttachBodyButtonSetting` = 對**單一節點**施加 k=600 的彈簧力;先前的 probe 直接搬動幾十個
節點的座標,等於位移控制、無限剛硬,**高估了拉力**,這是先前量測過於樂觀的原因)。**[實測]**:

固定拉法,只改變「抓取點離裂尖的距離 d」:

| d | 場 p98(σ₁) | 裂尖驅動力 | c 最大 | 裂縫成長 |
|---|---|---|---|---|
| 0.89 | 325 | **2407** | 190 | 4 → **223** |
| 1.85 | 174 | 68 | 5.2 | 4 → 58 |
| 4.03 | 149 | **25** | 1.07 | 4 → **13** |

**場的應力幾乎沒變(2 倍),但裂尖驅動力掉了 100 倍。** 元凶是 `_reach_drive` 的**硬性截斷**:

```
w = 1 − d/TEAR_REACH,  且 d > TEAR_REACH(=2.5)的元素直接排除
```

圓盤半徑 6.89,所以**只要抓的地方離裂尖超過圓盤半徑的三分之一,拉力就完全不算數**。
對照實驗把嫌疑一一排除:

- **鞏膜小帶錨定無罪**:取消錨定,d=4.03 的裂縫 13 → 14(等於沒差)。
- **截斷就是主因**:reach 2.5 → 8,同一拉法驅動力 25 → 2199、裂縫 13 → 87。

**修正**:取消截斷,改成物理形狀的衰減核 `w = 1/(1+(d/λ)²)`,`TEAR_REACH` 改成**衰減長度 λ**
(預設 3.0)而非牆;並用 **top-K 加權平均**(`CAP_TEAR_TOPK`,預設 8)取代裸 max,避免單一
接近退化的三角形(可達本體 100 倍)獨自驅動整條裂縫。修正後同一組拉法:

| d | 修正前裂縫 | 修正後裂縫 |
|---|---|---|
| 1.85 | 58 | **197** |
| 4.03 | 13 | **85** |
| 5.73(近周邊) | — | **58** |

且**抬升 0.15–0.2 就達到 c ≈ 1**(輕拉即起裂),全程退化元素 0.0%。

> [推論] 這個核函數在論文裡沒有對應物 —— Dequidt §4.3 只說用「裂尖鄰域」的加權應力。
> 粗網格的裂尖沒有應力奇異性(§5.3),所以「遠處的拉力如何抵達裂尖」必須額外建模;
> 硬性截斷是先前的權宜,`1/(1+(d/λ)²)` 則取薄板中載荷隨距離擴散的形狀,仍是**工程近似**。

### 4.5 次要限制:裂縫會走進死路,以及往周邊逃逸

驅動力修好後,新的限制變成**裂尖走進死路就永久停住**。兩種死法都實測到:

1. **鄰居全都走過**:`cand = [j for j in nbr[tip] if j not in self.crack]` 排除了**整段歷史**。
   但 CCC 的目標正是**繞一圈回到起點** —— 這條規則讓收口成為非法動作。實測:裂尖停在
   r=6.19,4 個鄰居全在 crack 裡,c 超過 100 卻永遠不動。
   **修正**:只排除最近 `TEAR_NOBACK`(8)格,並允許抵達**起始缺口**視為收口
   (`TEAR_CLOSE_MIN`=40 防止剛起裂就假收口 —— 若對任何走過的點都判定收口,裂縫會在
   58–115 格就提早結束,**比不修還短**)。
2. **轉角上限**:唯一的自由鄰居需要轉 153°(上限 70°)→ 真死路。

**尚未解決**:裂縫傾向**往外跑到周邊**(裂尖最終落在 r=5.3–6.6 / R=6.89),而不是沿圓周繞。
掃描顯示收緊轉角只是讓它跑更遠(70°→25°:裂縫 197→242,但 r 5.28→6.58),纖維比拉到 6.0
反而讓裂縫找不到合法方向(只長 7 格)。這正是臨床的 **Argentinian-flag 逃逸**,也和 §5.2 的
網格量化同源;要真正沿圓周走需要**沿路徑重網格**([`ccc_method/2`](../ccc_method/2_topological_remesh.md))。

### 4.6 「拉不開」的真正主因:剝離門檻在幾何上**不可達**(與撕裂無關)

比撕裂判據更早擋住一切的,是**黏附**。兩個各自合理、合起來卻互相矛盾的常數 **[實測]**:

```
中位邊長 e        = 0.300
MAX_STRETCH      = 1.6      → 單一黏著節點最多能抬 √((1.6e)²−e²) = 0.375
break_lift       = BREAK_FORCE/ADHESION_STIFF = 60/120 = 0.500   ← 大於 0.375
```

**應變夾限在 0.375 就把節點擋住,而脫黏需要 0.500 —— 內部任何一點,無論用多大力,都永遠
不可能脫黏。** 實測:對中央節點拉出 10.6 單位長的滑鼠箭頭(施力 6384),節點只抬升 1.36,
2153 個黏附點只放開 65 個(全在裂縫旁,因為裂縫製造了新的自由邊)。囊膜等於焊在水晶體上。

這個 bug **從外面完全看不出來** —— 拉了就是沒反應。修正:`BREAK_FORCE` 60 → **30**
(break_lift 0.250,落在 0.375 內),同一拉法放開 **282** 個點、抬升 1.36 → 1.97。並加上
`_check_peel_reachable()`,開場就把兩個數字印出來比對,不可達時大聲警告。

**另一半是剝離規則**:`PEEL_FRONT_ONLY` 只允許「已脫黏區域的邊緣」放開,但一開始整個圓盤都
黏著,唯一的邊緣是外圈網格邊界 —— 而撕裂模式下外圈被鞏膜小帶錨死。於是中央永遠沒有合格的
節點。新增 `PEEL_NUCLEATE`:用力夠大時任何位置都能**成核**(成核比擴展難,是正確物理)。

> [補充] 即使修好,**用滑鼠拉「一個點」也只能拉出一個小凹陷** —— 這是對的物理。真實撕囊
> 能大片剝離,是因為外科醫師抓的是**已經撕開的瓣**(只剩撕裂前緣連著)。所以「拉到哪剝到哪」
> 要成立,前提是先有一片瓣。

### 4.7 撕裂方向必須來自**裂尖自己**(這是「裂縫跟我拉動無關」的原因)

實測拉動過程中,各候選方向來源與「裂尖→手」方向的夾角 **[實測]**:

| 方向來源 | 與「裂尖→手」夾角 |
|---|---|
| **裂尖自身的局部 σ₁** | **0.7° – 14.5°** |
| 寬核 top-K 平均(曾用) | 24° – 85° |

寬核平均被**手底下**那批元素主導,所以它的角度是「手那裡的應力方向」,套到裂尖沒有幾何意義。
後果實測:抓方位角 0° 與 180°(完全相反兩側)裂尖都停在 −100° 附近;相同拉法兩次,裂尖一次
r=6.42、一次 r=1.45。

但局部**大小**單獨也沒用(0.3–20,門檻 20),因為粗網格裂尖沒有應力奇異性(§5.3)。
**修正**:張量的**方向與雙軸比取自裂尖**,再**縮放到寬核回報的驅動量**;並加 `TEAR_LOCAL_MIN`
門檻 —— 無載荷時局部方向是數值雜訊,放大雜訊正是裂縫在你還沒拉之前就衝到邊緣的原因
(錄製資料:t=0.82→1.42s 裂尖 r 2.01→6.58,c 飆到 193)。

**其他同批修正**:每次機會只前進**一條邊**(先前一次 4 條共用同一次應力評估,裂縫吃的是自己
已經釋放掉的應力,所以停不下來);`TEAR_ARREST` 卸載即止(放手後 +35 格 → +0~1);
`_build_vtris` 向量化 **49 ms → 1.38 ms**(`np.unique(axis=0)` 佔了 7.48 ms 中的 6.10 ms,
改用 1-D 整數鍵),撕裂開銷 14.8 → 6.5 ms/step。

> ⚠️ **量測方法的教訓**:先前的 probe 手動呼叫 `onAnimateBeginEvent`/`EndEvent`,但
> `Sofa.Simulation.animate()` **本身就會派發**(實測 10 次 animate → 10 begin/10 end)。
> 於是每步的撕裂與黏附邏輯跑了**兩次**,撕裂速率高估約 2 倍、step 成本也高估約 2 倍。
> 更早的 probe 甚至直接**搬動節點座標**(位移控制 = 無限剛硬),而真實滑鼠是
> `AttachBodyButtonSetting` 的 k=600 彈簧**只抓一個節點**。凡回報手感數字,probe 必須先證明
> 自己複製的是真的互動路徑。

### 4.8 剝離力學:前緣線 vs 整片垂直硬扯(「怎麼拉都是小裂縫」的主因)

「輕輕一拉就應聲撕開、抓著往哪拉哪裡就整片 deattach」做不到,是因為黏附模型算的是**錯的
力學**。原本每個黏附點**各自**要抬到 `break_lift` 才放開 —— 那是「把整片貼紙垂直拔起來」;
真實剝離(撕皮、撕貼紙)的功**集中在前緣那條線**上,所以輕輕一拉就能一路開下去。

**修正**:前緣(已有脫黏鄰居或位於網格邊界)的門檻改為 `break_lift × PEEL_FRONT_EASE`,
遠低於在完好材料上**成核**所需的門檻。實測(同一段拉動,黏附點共 2156)**[實測]**:

| `PEEL_FRONT_EASE` | 仍黏附 | 已脫黏 |
|---|---|---|
| 1.0(舊行為) | 1827 | 329 |
| 0.5 | 1600 | 556 |
| **0.15**(新預設) | **1072** | **1084 ≈ 半片** |
| 0.08 | 764 | **1392(65%)** |

全程不自啟動、放手即停、無爆炸(maxcoord 6.89、最大邊拉伸 1.60)。

**另一道獨立的牆:力預算。** 每單位面積 14.5 個黏附點 × 每點 30 的抓力:

```
半徑 2.0 的圓片 → 需要  5450
半徑 3.0 的圓片 → 需要 12262   ← 接近真實撕囊尺寸
滑鼠能給:MOUSE_STIFFNESS(600) × 拖曳距離,拖 10 單位 = 6000
```

> [補充] 真實尺寸的囊膜圓片需要的力約為滑鼠所能給的 **2 倍**,所以「整片拉走」不是調撕裂
> 參數能解決的。把黏附力減半、減到三分之一,放開的點只從 329 → 415 → 432(邊際效益很小)
> —— 因為瓶頸是**前緣傳播規則**,不是總抓力,這也正是上表把前緣門檻放鬆才有效的原因。

### 4.9 檢視器:讓「現在發生什麼事」可以逐幀讀出來

瀏覽器頁面現在逐幀呈現撕裂判據的**每一項**,而不只是結果:

- **左下「撕裂判據」面板**:σ₁、σ₂、θ₁、d(argmax c)、**σ_u**(Eq.3)、σ̄_T、f 纖維方向、
  **σ̄_u**(Eq.4)、**c = σ_u/σ̄_u**(Eq.1)、裂尖局部 σ₁(閘門)、裂縫長度/裂尖 r、
  器械拉力與位置,最後是這一幀的判定字串。拖時間軸會用**那一幀自己的紀錄**重畫。
- **洋紅粗線**:已撕開的裂痕(mesh 邊的串接),黑框+白襯以在滿版熱圖上仍可辨識;
  ● 起始缺口、○ 目前裂尖(帶脈衝環)、**青虛線 = 下一步的 argmax d 方向**。
- **黃點 + 箭頭 = 你的器械**:位置與施力方向,箭頭長度隨力大小。來源是 SOFA 自己的
  `MechanicalObject.force`(滑鼠彈簧幾乎只載入單一節點,argmax|f| 精準指認被抓的節點 ——
  已對已知節點驗證:argmax 完全吻合,2171 個節點中只有 5 個超過峰值的 10%)。

> ⚠️ 版面經瀏覽器實測驗證(headless 載入 + 幾何量測):四組面板無重疊、判定列可見、
> 0 個 console error、0 個失敗請求。先前檢視器面板互相遮蓋過,是量過才發現的。

### 4.10 本質原因:裂尖沒有應力奇異性,判據沒有裂縫長度,而網格擋掉一半的推進

從**使用者實際 session 的紀錄**(非 probe)算出來的三個數字 **[實測]**:

**(1) 裂尖只感受到全場應力的約 3%。**

| t (s) | 裂尖 σ₁ | 裂尖局部 σ₁ | 全場 p98 | 局部/全場 |
|---|---|---|---|---|
| 8.4 | 189 | 3.92 | 114 | 0.034 |
| 13.9 | 103 | 0.95 | 84 | 0.011 |
| 22.2 | 10014 | 1.70 | 291 | **0.006** |
| 36.0 | 87306 | 22.6 | 955 | 0.024 |

真實裂尖是**應力奇異點**(σ→∞),所以真材料從既有缺口一撕就開。粗線性三角網格把應力平均在
0.3 單位寬的元素上,**根本無法表現奇異性** → 裂尖低估約 **30 倍**。`TEAR_TIP_GAIN=1.5`
是在補這 30 倍,杯水車薪。同一份紀錄顯示器械離裂尖的距離中位數是 **4.30**(圓盤半徑 6.89),
所以幾乎永遠處在「拉的地方裂尖感覺不到」的狀態。

**(2) 判據完全沒有裂縫長度項。** 斷裂力學的 `K = σ√(πa)` —— 驅動力隨裂縫長度的**平方根**
成長,這正是「越撕越開」的來源。原本的判據裡 100 格的長裂縫和剛戳的小洞一樣難撕,所以它
永遠「跑」不起來。新增 `TEAR_LEFM`,以裂縫**空間範圍**(路徑外接盒對角線)算 √(a/a₀)。

> [推論] 用外接盒對角線而非首尾距離或頂點數:首尾距離對 CCC 想要的「繞回來」形狀會塌成 0
> (實測 41 格的裂縫算出放大倍率 1.00,等於沒作用);頂點數則會獎勵原地打轉的鋸齒路徑。

**(3) 判據通過後,55% 的推進被網格擋掉。** 這是最大的單一損失,而且**先前完全看不到** ——
推進失敗時遙測仍記為 `"tearing"`,**紀錄在說謊**。修正為回報真正的失敗原因後:

```
判據通過但推進失敗:150 步(18.6%),全部是「需要轉 ~90°,上限 70°」
c ≥ 1 的 273 步中,150/273 = 55% 是被網格擋的,不是被物理擋的
```

原因是**轉角上限比網格自身的角度解析度還小**:每個頂點約 6 條邊、間隔 60°,前方的邊被自己
走過後,最近的合法選擇就落在 85–95°。`TEAR_TURN_MAX` 70 → **100**:

| 轉角上限 | 裂縫長度 | 在撕的步數 | 被網格擋下 |
|---|---|---|---|
| 70(舊) | 45 | 15.2% | **18.6%** |
| **100**(新) | **90** | **31.9%** | **0** |
| 130 | 90 | 31.9% | 0 |

> ⚠️ **「力氣不夠」是錯的診斷。** 同一段拉動把施力加到 **9 倍**(5790 → 53272):抬升 2.35 →
> 7.22、剝離 1017 → 507 都有反應,但**裂口張開只從 0.62 到 0.68、裂縫長度完全沒增加**
> (127 → 115)。所以調高 `MOUSE_STIFFNESS` 不會讓裂縫更開 —— 力氣對**剝離**有效,對**裂縫**無效。

### 4.11 全面檢討:剝離跑贏撕裂,加上三個遙測 bug

使用者回報「sofa app 上沒有真正被拉開;heatmap 的裂痕在某一幀出現後就再也沒變過」。查紀錄
後,裂痕其實是逐格長的(frame 84→89:4→5→6→8→10→12→14→16,0.7 秒 6 幀,看起來像瞬間),
但**在 t=10.78s 停在 16 個頂點後,剩下 33 幀(約 4 秒)完全沒有再動**。原因如下。

**主因:剝離跑贏撕裂,並把撕裂餓死。** **[實測]**

```
t=0.0–4.9   glued 2153   crack 4      無事發生
t=5.7–8.2   glued 1885   crack 4      ← 剝離猛跑,裂縫完全沒長
t=9.0–10.9  glued 1747   crack 4→16   裂縫短暫成長
t=11.5      glued 1468   crack 16     ← 剝離加速,裂縫凍結
t=14.8      glued 1323   crack 16     裂縫已死,剝離又多放開 424 個點
```

裂尖周圍一旦脫黏,那片膜就**鬆了** → 應力歸零 → 裂尖永遠感覺不到力 → 裂縫**永久**死亡。
凍結後裂尖局部 σ₁ 固定在 0.46,而器械施力高達 |F|=6449 也毫無作用。

**這是把「剝離」和「撕裂」寫成兩套獨立機制的結果。** 真實撕囊裡瓣是**因為撕裂前進才脫離**的
—— 是同一件事。新增 `PEEL_NEAR_CRACK`(預設 3.0):脫黏前緣不得跑在裂縫前方太遠。掃描:

| `PEEL_NEAR_CRACK` | 裂縫 | 脫黏數 |
|---|---|---|
| 0(不限,舊行為) | 90 | 1058 |
| 1.6 | 30 | 310 ← 太緊,反而餓死剝離 |
| **3.0**(新預設) | **86** | **804** |

**三個遙測 bug(全部會誤導判讀)**:

1. **閘門擋下時不更新測量值** → 面板顯示的是**上一次**的 σ₁/loc/σ_u。實測畫面同時出現
   `loc = 0.46`(高於門檻 0.4)和「裂尖未受力」,自相矛盾;凍結後 9 幀的 tipS1 一直是 51.4、
   loc 一直是 0.46,而 |F| 在 5973→33 之間劇烈變動 —— **數字是死的**。
2. **座標空間混用**:`tipx/tipy` 用**變形後**座標,`pull.x/y` 用**靜止**座標。兩者相減得到
   9.68,大於圓盤半徑 6.89 —— 不可能。§4.10 那句「器械離裂尖中位數 4.30」就是這個 bug 的
   產物,**該數字作廢**。現在裂尖一律以靜止座標發佈,與參考圓盤、器械標記同一空間。
3. **纖維方向用變形後座標算**。纖維是**材料屬性**,應該用靜止座標;否則纖維場會跟著拉動旋轉,
   而真實膠原不會。

**檢視器新增「黏著 / 脫離」圖層**(這是先前完全缺席的資訊):逐頂點的黏附狀態以每頂點一字元
的字串發佈(約 2 KB,相對於幀內既有的約 100 KB 應力陣列),畫面上**變暗的格子 = 已脫離**,
**青線 = 剝離前緣**(黏著與脫離的交界,也就是下一個會鬆脫的地方),HUD 顯示仍黏著/已脫離的
數量與百分比。第一次打開就直接看到問題:**整個內部已經脫離、前緣在 r≈5,而裂縫只是 r≈1–2
的一小圈** —— 剝離遠遠跑在撕裂前面。

### 4.12 爆炸防護的缺口,以及紀錄盒 / 圖層

**爆炸沒有被接住。** 使用者回報「看不到裂痕,整片 mesh 拉到最後皺起來」。紀錄顯示力學在爛掉
**[實測]**:邊拉伸峰值 **20.78**(夾限 1.6)、|coord| 峰值 **13.49**(圓盤半徑 6.89),而
**`rewinds = 0`** —— 回滾一次都沒觸發。兩個原因:

1. **`MAX_COORD = 50` 對這個尺寸毫無意義**:節點飛到 13.49 早就爛了,離 50 還很遠。新增
   `STRAIN_PANIC`(預設 4.0,單位是 `MAX_STRETCH` 的倍數):邊被拉超過 6.4 倍就判定為爆炸。
   座標小又有限的「皺成一團」用 `MAX_COORD` 永遠看不到,用邊拉伸則一目了然。
2. **撕裂會讓回滾機制永久失效**(較嚴重):回滾在快照頂點數與當前網格不符時會拒絕執行,而
   每次分裂都會增加一個頂點 —— 快照要等到下一個「健康」幀才會重建;可是網格一旦劣化就**再也
   沒有健康幀**,於是安全網從此關閉。修正:分裂時同步把快照長大(複製該唇的項目)。

**紀錄盒不再被覆蓋**:`diag_last.csv` 改為輪替保留 `diag_last.prev.csv`。這是實際踩到的
坑 —— 分析途中跑了幾個 probe,使用者那次 session 的 CSV 就被蓋掉了,而那正是最需要它的時候。

**歷史紀錄可跨 app 重開檢視**:每個 take 本來就以逐行方式寫入 `stress_log_<id>.jsonl`,
所以暫停或關閉 SOFA 的當下紀錄就是完整的 —— 但瀏覽器先前只看得到還在記憶體裡的 take,程序
一結束就消失。現在 `/sessions` 會把**磁碟上的檔案也列為 take**,`/frame?s=f:<檔名>&i=N`
直接從檔案讀。索引是惰性建立的(依 size+mtime 快取),而列表只做分塊換行計數 ——
逐行掃描一個 159 MB 的舊 log 會讓請求超時,結果就是**一個磁碟 take 都列不出來**;
改成分塊計數後同樣的列表只要 **0.107 秒**。

> [補充] tail 視窗必須大於單一幀:一幀 JSON 約 100 KB,原本用 64 KB 的視窗去讀檔尾,
> 永遠讀不到一行完整的 JSON,所以每個 take 的結束時間都顯示 0.0。

**圖層獨立開關**:應力 σ₁ / 黏著·脫離 / 裂痕 / 器械接觸 / 方向線 / 網格線,各自可勾選,
也可全開疊看。每個開關都在真實瀏覽器裡驗證過**確實會改變畫面**(關掉後畫布像素校驗和改變),
七個面板兩兩無重疊,0 console error。

### 4.13 一次紀錄的定義,以及面板整理

**定義**:一個 **take = 一次場景執行**。在 SOFA 按重新整理會重載場景,`createScene` 因此把
上一段錄製歸檔並開一個新檔 —— 與使用者的認知一致。但**一個 take 裡通常有很多次拉動**
(拉→放→換個地方拉→暫停→繼續),所以 take 不等於一次手勢。

**每次「抓住→放開」編號為一個 pull**,時間軸上以色帶呈現,可點擊跳轉,並有 ⟨ ⟩ 前後切換。
`PULL_GAP`(0.35 s)避免拖曳中的瞬間鬆手把一次手勢切成兩段。

> ⚠️ **拉動偵測不能用力量大小。** 實測:沒人碰時 `max|F| = 0.0`、拖曳中約 137,但**放手後的
> 回彈峰值 1754** —— 比拖曳本身還大。任何能忽略回彈的門檻也會忽略輕拉。改用
> `_is_grabbing()`(偵測滑鼠互動器在場景圖中的物件)判斷「有沒有在拉」,再用 argmax|f|
> 判斷「拉的是哪個節點」。

**歷史紀錄跨 app 保存**:見 §4.12。take 選單同時列出記憶體中的與磁碟上的錄製。

**面板整理**:每個面板的標題可點擊摺疊(狀態記在 localStorage),長篇說明文字有單一開關
可整批收起。實測 tear 控制面板摺疊後由 390 px 縮到 40 px。

> ⚠️ **兩個只有實測才會抓到的 bug**,都出現在這輪:
> 1. `updateTimeline()` 裡我把 `seek.value` 的同步寫在 `const shown` **宣告之前**,於是
>    **每次進入回放模式都丟出 TDZ ReferenceError**,標籤永遠停在 LIVE —— 看起來就像跳轉
>    按鈕和色帶「完全沒反應」,實際上是狀態改了但畫面永遠不更新。
> 2. live take 的 `/segments` 對**整個歷史緩衝區**逐幀 `json.loads`(最多 1500 幀 × 約
>    100 KB),而頁面每 55 ms 就問一次 → 伺服器被灌爆、`/stress` 被餓死,**頁面看起來凍結**
>    而模擬其實跑得好好的。改成只讀每幀前 4 KB 用正規式取值,並把輪詢降到 2 秒一次。
>
> 另外記一筆量測陷阱:從瀏覽器自動化的 isolated world 讀 `el.onclick` 或
> `window.__x` **一律得到 null**,即使處理器確實掛上了。用它當「處理器沒掛上」的證據會白追
> 很久;可靠的訊號是 DOM 文字與實際行為。

### 4.14 「前面都沒變、最後突然出現一圈」——是檢視器把圖層擋掉了

使用者回報回放某個 take 時,黏著圖層與裂痕**整段都沒變化,最後才突然出現**。查紀錄,資料
本身是**完全漸進**的 **[實測]**:黏附 2153 → 1170、裂縫 4 → 72,逐幀增加。

問題在檢視器:這個 take 有 **42 個不同的 `gver`**(每次頂點分裂就跳版),而頁面只持有**一份**
參考圓盤(最新的那版)。裂痕與黏著圖層都寫了 `cur.gver === geomVer` 的守衛,於是**只有最後
幾幀畫得出來**。

**修正**:移除版本相等的要求。分裂**只會 append 頂點**,所以舊幀引用的索引在新的頂點陣列裡
仍然指向同一個位置;尚未存在的頂點沒有對應字元,視為「仍黏著」。

**同時發現一個會毀掉歷史的 bug**:take 檔名只用 session 編號,而 session 編號**每個行程都從
1 重新開始** —— 於是每次啟動 app 都以 `"w"` 重新開啟 `stress_log_1.jsonl`,**把上一次啟動的
第一個 take 直接覆蓋掉**,正好是你最想回去看的那一份。改為以行程啟動時間戳命名
(`stress_log_<MMDD>_<HHMMSS>_<n>.jsonl`),take 才會跨執行累積;選單顯示為「08-20 16:27 #1」。

### 4.15 裂縫路徑的鋸齒:轉角上限與「航向慣性」要分開

§4.10 把 `TEAR_TURN_MAX` 從 70° 開到 100°,是為了讓裂尖不要在網格自身 60° 的邊間距上撞死。
但那同時也讓**航向本身**每一步都能擺動 100°,於是路徑變得鋸齒、又容易折返後把自己堵死。

**兩件事要分開**:裂尖仍可在分散的鄰居中**選擇**,但它據以前進的**航向**應該平滑轉動 ——
真實的撕裂有動量,術者的拉動方向也是慢慢變的。新增 `TEAR_DIR_INERTIA`(預設 0.6):新方向
與前一個航向做加權混合(裂向是**直線**不是箭頭,所以混合前先對齊正負號)。

實測(同一段拉動,量相鄰切割邊之間的轉角):

| 慣性 | 裂縫長度 | 每邊轉角中位數 | 平均 |
|---|---|---|---|
| 0(舊行為) | 4 | — | — |
| 0.4 | 35 | 3.9° | 14.0° |
| **0.6**(預設) | **100** | **3.1°** | 4.9° |
| 0.8 | 131 | 2.6° | 4.0° |

**慣性讓路徑同時變平滑又變長** —— 因為鋸齒本身就是把自己走進死路的主因。預設取 0.6 而非
0.8,是為了保留「手動轉向」的操控性:慣性太高,裂縫就不太理會你拉的方向了。

### 4.16 黏附的方向性:使用者指出的建模錯誤,以及實測為何仍不足

使用者的觀察:**「attach 的力量應該只存在於表面切平面方向,不應該有往下吸住橢球基座的力。」**
這是對的。前囊是**躺在**水晶體上,靠的是面內連續性與懸韌帶錨定,不是被吸附在圓頂上。
而 `RestShapeSpringsForceField` 把每個節點拉回其靜止位置是**完整 3D 的**,所以掀起瓣時要對抗
一條把它往下拉的彈簧。

**實作**:`ADH_TANGENTIAL` —— 錨點移到自己的子節點(無 solver),controller 每步把錨點沿
**水晶體表面法線**滑到 `anchor = rest + n·((P−rest)·n)`,如此彈簧力 `k(anchor−P)` **在建構上
就沒有法線分量**。彈簧本身保留(隱式積分,穩定)。

**但實測沒有帶來預期效果** **[實測]**,同一段拉動:

| 模式 | 抓取點抬升 | 抬升>0.5 的節點 | 裂縫 | 仍黏附 |
|---|---|---|---|---|
| 完整 3D(原本) | 2.34 | 287 | **100** | 1044 |
| 純切向 | 2.36 | 303 | **47** | 1388 |

抬升幾乎沒變(2.34 → 2.36),**撕裂卻少了一半**(膜更容易讓步 → 應力累積更少 → 撕得更少)。

> **結論:往下的吸附力從來不是掀不起瓣的原因。** 真正的限制是**膜的可拉伸量**(應變夾限)
> 加上**鄰居的面內錨定** —— 要掀起一大片,得先讓那一片在面內脫離,而那是剝離前緣的工作。
> 因此預設關閉(`CAP_ADH_TANGENTIAL=1` 可開啟):保留它是因為它確實是更忠實的模型,
> 等「掀瓣」真正解決後應以它為基礎,但目前開啟只會讓撕裂變差而沒有補償。

> ⚠️ 順帶修掉一個顯示缺陷:面板摺疊箭頭的 CSS escape `be` 在寫入時掉了一層反斜線,
> 於是每個面板標題前都印出字面的「be 」(截圖可見)。改用實際字元 ▾ / ▸。

### 4.17 論文模式(`-Paper`):只跑 INRIA 發表的設定

依 [`reference/8` 附錄 A](../reference/8_inria_implementation_deepread.md) 的查證結果建立,
用來把**論文的方法本身**和**本 demo 自己加的東西**分開評估。

|---|---|---|
| 材料 | `TriangularAnisotropicFEMForceField`,co-rotational(`method="large"`) | Marchal §2.1「transversely isotropic FEM formulation using triangular elements」 |

`youngModulus` / `transverseYoungModulus` / `poissonRatio` / **`fiberCenter`**,

### 4.18 論文模式的實測:拿掉黏附,幾乎沒有差別

同一段拉動,唯一差別是有沒有黏附/剝離 **[實測]**:

| | 切開長度 | 抓取點抬升 | 抬升>0.5 的節點 |
|---|---|---|---|
| 目前預設(mass-spring + 黏附 + 剝離) | **131** | 2.15 | 202 |
| 論文模式(**完全無黏附**) | **128** | 1.62 | 176 |

**把黏附整個拿掉,撕裂長度 131 → 128、抬升 2.15 → 1.62 —— 幾乎沒有差別。**

> §4.16 的切向黏附實測(2.34 → 2.36)當時已指向同一個結論,這裡是獨立的第二個證據。

### 4.19 「加了 -Tear 就翻不動了」的真正原因:懸韌帶錨定

使用者的關鍵回憶:**「原本不用 -Tear 模式時可以直接把整個周邊拉起來翻折,加上撕裂之後就沒有
這種變形了。」** 這句話直接定位了原因 —— `-Tear` 只改了一件與可動性有關的事:

```python
FIX_OUTER_RIM = ... "0"      # 預設:外緣 FREE   ← 你記得能翻折的模式
if CAP_TEAR:
    FIX_OUTER_RIM = ... "1"  # 撕裂模式:外緣錨定 427 個節點
```

同一段「抓外緣、往上並往中心翻折」的動作 **[實測]**:

| 模式 | 抓取點抬升 | 抬升>1.0 的節點 | 抬升>3.0 | 切開 | 最大邊拉伸 |
|---|---|---|---|---|---|
| 無 `-Tear`,外緣 free | **8.93** | 1284 | 799 | 0 | 1.12 ✅ |
| `-Tear`,外緣**錨定**(現行預設) | **0.98** | **0** | **0** | 11 | 1.07 |
| `-Tear`,外緣 free | **5.69** | 728 | 326 | **61** | **24.45** ⚠️ |

**錨定時抬升 0.98、沒有任何一個節點升過 1.0 —— 膜是真的完全動不了。** 這不是「元件不支援立體翻
折」(無 `-Tear` 時同樣的元件抬到 8.93),純粹是邊界條件把它釘死了。

**放開外緣就能翻折,而且照樣撕**(切開 61 格)。代價也是真的:外緣 free **加上**進行中的撕裂
會讓邊拉伸到 **24 倍**(上限 1.6)。**這不是夾限迭代不夠** —— 實測 3 / 12 / 40 次迭代分別給出
24x / 150x / 38x,增加迭代反而更糟,所以過度拉伸另有成因,那是下一個要解的問題。

**開關**:`./Capsulorhexis/scenes/run_cap.ps1 -Tear -FreeRim`(或 `CAP_FIX_RIM=0`)。

> ⚠️ 順帶修掉一個誤導訊息:應變 panic 觸發回滾時,座標守衛的訊息也會一起印出
> 「a node passed |coord|>50 (max 6.9)」—— 6.9 根本沒有超過 50。兩個守衛現在分開回報,
> 才看得出實際是哪一個觸發的。

> [補充] 這也修正了 §4.18 的推論。當時說「限制在膜本身的可拉伸量」是**不完整**的:
> 更直接的限制是**外緣錨定**。§4.18 的比較(有無黏附)兩組**都是錨定的**,所以兩組都抬不起來
> —— 那個實驗證明了「黏附不是主因」,但沒有暴露出真正的主因。

### 4.20 脫黏門檻低於「彈性雜訊底線」——整片假性脫離

量測證實這是**真的 bug**,而且是 §4.8 我自己引入的。

**先量底線**:離拉點很遠、純粹彈性回應、完全沒有掀起的節點,位移是多少 **[實測]**:

### 4.22 「撕破皮」需要的是裂口張開,而裂口幾乎不張開

使用者更正了先前的想法:**不需要先繞完一圈**,像撕破皮那樣「有一段裂痕就能掀起一側,邊掀邊撕」
才是目標(論文 Fig.3 的 shearing / ripping)。這是對的,並且把關鍵指標從「收口」改成
**裂口是否張開** —— 不張開就沒有瓣可抓。

**實測「抓住裂縫旁邊、往上掀」** (裂口張開量 = 各對唇的分離距離)**[實測]**:

| 設定 | 切開 | 裂口最大/平均 | 抬升 |
|---|---|---|---|
| 預設(黏附 + 外緣錨定) | 45→99 | 0.73 / **0.21** | 1.92 |
| 無黏附(論文模式) | 46→139 | 0.33 / **0.07** | 1.39 |
| 無黏附 + 外緣 free | 46→104 | 0.29 / **0.03** | **8.16** |
| 黏附 + 外緣 free | 43→73 | 15.02 / 1.15 | 4.32(過度拉伸) |

**裂口在任何設定下都幾乎不張開。** 特別是「無黏附 + 外緣 free」抬升高達 8.16 卻只張開 0.29 ——
**整片一起移動,而不是一側掀起**。抓單一節點會把裂縫**兩側**一起帶起來(兩側在裂尖繞過去仍相連),
所以永遠形成不了瓣。

### 4.23 排除法:抬升上限由**膜的面內剛度**決定,不是夾限也不是彎曲

抬升在多組設定下**固定在 1.92** —— 這個「不變」本身就是線索。逐一測掉 **[實測]**:

| 參數 | 值 | 抬升 |
|---|---|---|
| `BEND_STIFFNESS`(彎曲) | 15 / 3 / 0.5 / **0** | 1.92 / 1.92 / 1.92 / **1.92** ← 無關 |
| `MAX_STRETCH`(應變夾限) | 1.6 / 3.0 / **關閉** | 1.92 / 1.92 / **1.92** ← 無關 |
| **`EDGE_STIFFNESS`(面內剛度)** | 2500 / 800 / 250 / 120 | **1.92 / 3.24 / 5.74 / 8.01** ✅ |

**外緣錨定時,要掀起就得把膜拉成錐面,而錐面深度由面內剛度決定。** 這也更正了先前多處把
「膜的可拉伸量 / 應變夾限」當成限制的推論 —— 夾限完全關閉都不影響抬升。

> ⚠️ 但**放軟不能只放軟**:E 從 2500 降到 120,抬升 1.92 → 8.01、裂口 0.73 → 1.48,
> 但切開量 99 → 46。試著把 σ̄_T 按 σ ∝ E·ε 等比例下調(20 → 1)**沒有救回來**。
> 原因是 **mass-spring 模式的應力觀測器用的是固定的 `STRESS_E`,與 `EDGE_STIFFNESS` 無關**
> (程式碼早有註明:此模式沒有連續體 E,數值只是幾何應變尺標)。所以「調軟膜 + 等比例調門檻」
> 這條路在目前架構下不成立 —— **觀測器與真實膜剛度是脫鉤的**,這是要先解的結構問題。

`CAP_EDGE_STIFFNESS` / `CAP_MAX_STRETCH` / `CAP_BEND` / `CAP_EDGE`(網格解析度)現在都可由
環境變數調整,上述每一列都可重跑驗證。

### 4.24 ⭐ 真正的元凶:`topo.edges` 從未更新,舊彈簧把裂口釘死

**這一條解釋了整個 demo 長期的兩大症狀**,而且是同一個 bug。

追問「為什麼 edge springs 存在,裂口就張不開」,一路量下來 **[實測]**:

```
topo.edges            : 6321   ← 拓樸容器的邊表,從未更新
由 triangles 推出的邊  : 6389   ← 真正的當前網格
在 topo.edges 但已不是三角形邊(陳舊):129
是三角形邊卻不在 topo.edges(遺漏):197
springs 集合 == topo.edges ?  True
```

`_split_vertex` 是**直接寫 `topo.triangles.value`** 來改接三角形的,繞過了
`TriangleSetTopologyModifier`,所以**拓樸容器自己的邊表永遠停在舊狀態**。而
`MeshSpringForceField` 的彈簧**完全等於 `topo.edges`**。後果是兩個,正好對應長期的兩大症狀:

| 陳舊邊 129 條 | **彈簧橫跨裂縫、把它釘死** |
|---|---|
| | 實測:**100%** 落在裂縫一個邊長之內(中位距離 0.149),而且被撐在 **1.04×** 靜止長度 —— 幾乎沒有伸長,就是釘書針。這就是裂口無論怎麼拉都只有 0.2–0.7 的原因。 |
| **遺漏邊 197 條** | **真實的邊完全沒有彈簧支撐** |
| | 無支撐的材料就是先前那些 20×、150× 的失控拉伸與尖刺的來源。 |

**修正兩步**(缺一不可):

1. 分裂後由當前三角形**重建 `topo.edges`**。
2. **重新建立** `MeshSpringForceField` 元件,而不是 `reinit()` —— 實測即使 `topo.edges` 已修正,
   `reinit()` 仍然把彈簧留在舊的 6321 條;移除元件再新增才會重建(陳舊 125 → **0**)。
   該元件只在 **init 時**讀取拓樸。

**效果**(預設 mass-spring、`EDGE_STIFFNESS=2500`,**完全沒有調軟**):

| | 修正前 | 修正後 |
|---|---|---|
| 切開 | 45→99 | 33→95 |
| **裂口最大** | **0.73** | **8.75**(12×) |
| **裂口平均** | **0.21** | **2.53** |
| **抬升(裂縫旁掀起)** | **1.92** | **7.25**(3.8×) |
| 抬升(中央拉) | 1.95 | **7.74** |
| 爆炸次數 | — | **0** |
| 網格健康 | — | 拉伸 1.52、退化 0.1% |

> ⚠️ **這推翻了本檔多處先前的歸因。** §4.23 說抬升上限由 `EDGE_STIFFNESS` 決定 ——
> 那是**症狀不是病因**:調軟之所以有效,只是因為把釘書針一起調弱了。修正之後,
> **在原本的剛度下**就能同時得到大裂口與大抬升,完全不需要犧牲撕裂量。
> 同理,先前把過度拉伸歸因於夾限迭代不足、把翻不動歸因於黏附或外緣錨定,都只碰到表層。

> [補充] 根治的做法是改用 `TriangleSetTopologyModifier` 的 API 做拓樸修改,讓所有依賴拓樸的
> 元件收到變更事件;目前是在事後補正邊表 + 重建元件。`CAP_TEAR_SPRINGREBUILD` 可調重建頻率
> (預設 1 = 每次分裂,最正確,每次約 27 ms)。

### 4.25 重建彈簧的代價:抬升解鎖了,但約 1/3 的拉動會失控

把 §4.24 的修正拆成兩半分別量,可以看清楚各自負責什麼 **[實測]**:

| | 抬升 | 最大拉伸 | 退化 | 爆炸 |
|---|---|---|---|---|
| **只修 `topo.edges`**(不重建元件) | 1.95 | 1.60 ✅ | 0.1% ✅ | **0** ✅ |
| **加上重建元件** | **5.06–7.97** ✅ | 1.50–1.60 ✅ | 0.1–0.4% ✅ | 多數 0 |

**解鎖抬升的是「重建元件」那一半** —— 只修邊表不重建,彈簧仍是舊的那 6321 條,釘書針還在。

**但重建也帶來間歇性失控**。同一段抖動拉動重跑三次:2 次乾淨、1 次出現 17 次
`[Runaway]` 回滾。平滑拉動重跑四次則全部乾淨(拉伸 1.50–1.60)。所以大約**三次會有一次**
在抖動的手下失控;守衛會回滾,所以是劣化而非毀滅,但畫面看得出來。

**已排除的成因**:

- **不是把拉伸態烤成靜止長度** —— 實測重建後彈簧的靜止長度是 0.3000,與 `rest_position`
  完全吻合(而非當前的 0.2997),**取的是靜止態,正確**。
- **不是在解算中途改動場景圖** —— 撕裂跑在 `onAnimateBeginEvent`(解算之前),已改為延後到
  步進結束後才重建;平滑拉動因此從 stretch 11.69 / 5 次爆炸變成 1.50–1.60 / 0 次,
  但抖動拉動仍有 1/3 機率失控,所以時序**只是部分成因**。
- **不是唇邊或零長度邊** —— 失控的那次去查,超過 3× 的邊數為 **0**、最短靜止邊 0.048,
  網格本身沒有病態元素。

**目前可用的取捨**(`CAP_TEAR_SPRINGREBUILD`):`1`(預設)= 每次分裂都重建,裂口會張開、
可以掀起瓣,代價是偶發失控;設成很大的值 = 回到穩定但掀不動的舊行為。

> 根治方向見 §4.24 末:改用 `TriangleSetTopologyModifier` 讓拓樸變更以**事件**通知所有元件,
> 就不需要「事後補邊表 + 整個換掉元件」這種粗暴做法,間歇失控很可能隨之消失。

### 4.26 改用正規拓樸 API:元件做好了,但整合進場景會 SIGABRT(未解)

§4.24 的根治方向是「用 `TriangleSetTopologyModifier` 的正規 API 改拓樸」。實作結果與現況:

**(1) 這件事在 Python 做不到。** 實測 SofaPython3 的繫結:我們的 modifier 在 Python 裡**確實是**
`Sofa.Core.PointSetTopologyModifier`,`addPoints` / `removePoints` **可以呼叫**;但
`TriangleSetTopologyModifier` **沒有被繫結**,所以 `addTriangles` / `removeTriangles`
從場景腳本**完全取不到**(列出物件屬性只有 Data 欄位加 `propagateToDOF`)。而分裂正好需要那兩個。

**(2) 因此寫成 C++ 元件** `TopologySplitEngine`(`Capsulorhexis` plugin,已可建置)。
因為 Python 也不能呼叫任意 C++ 方法,所以設計成 **Data 驅動**:場景寫入 `splitPoint`、
`movedTriangles`,再遞增 `request`。內部流程:

```
addPoints(1, ancestors={v}, coefs={1})   ← SOFA 自動內插新 DOF,位置/靜止位置/速度都正確,
                                            不需要場景手動接陣列
removeTriangles(moved, removeIsolatedEdges=true, removeIsolatedPoints=false)
addTriangles(同一批三角形,但把 v 換成新頂點)
```

`removeIsolatedEdges=true` 正是重點 —— **它會讓容器的邊表保持正確**。
(三角形的頂點組合必須在移除**之前**擷取,因為 `removeTriangles` 會把倖存者重新編號。)

**(3) 元件本身驗證通過**(`Capsulorhexis/tests/test_topology_split.py`,6 三角形扇形):

### 4.27 現在為何撕到一半就停:裂縫把自己困死(轉角上限擋下 74%)

修好釘書針之後,畫面上第一次出現**真正撕開的洞**(露出水晶體)和**被掀起翻摺的膜條**。
但撕到一半就停。從使用者這次 71 秒的紀錄統計 **[實測]**:

| 原因 | 佔比 |
|---|---|
| **`blocked`:轉角上限** | **73.7%** |
| tip not loaded | 12.9% |
| **實際在撕** | **9.9%** |
| arrested(卸載即止) | 3.4% |

而被擋下時,裂縫**要求轉的角度**:

```
中位數 145°   最小 102°   最大 179°     (上限 100°)
69% 的阻擋要求轉超過 120°,亦即幾乎是「往回走」
```

最後一次成長在 t=53.2s,之後**整整 18 秒拉動完全沒有任何進展**,裂尖停在 r=1.98。

**成因**:裂縫只能沿**現有網格邊**前進,而且不能走回自己最近走過的路。它一路蜿蜒(截圖裡那條
鋸齒狀的膜條就是),最後抵達一個頂點,**所有還沒走過的鄰居都在後方**。轉角上限(正確地)
拒絕往回撕,於是永久卡死。

> 注意:放寬轉角上限**不是解法**。中位需求是 145°,要放行就得允許裂縫幾乎原地折返,
> 那會讓它折疊在自己身上。而且 `_advance_to_best_neighbour` 已經是取「最對齊」的鄰居,
> 若它都超過上限,其餘候選只會更差 —— 沒有更好的選擇可挑。

**這正是 Dequidt §4.4 預告的那句話**:「restrict the potential fracture direction to an
existing edge … **However the resulting fracture will be highly dependent on the original
mesh**」。論文給的解法是第二條路徑:**允許任意方向 + 沿裂縫重新網格化**。

而重新網格化需要 `addTriangles` / `removeTriangles` —— 也就是 §4.26 那個已經寫好、
單元測試通過、但整合進場景會 SIGABRT 的 `TopologySplitEngine`。**所以下一步是明確的:
把那個 SIGABRT 查清楚,它同時擋住了重新網格化這條唯一的出路。**

### 4.28 更正 §4.27:網格**不是**纖維對齊,但裂縫其實有在跟著纖維走

§4.27 我寫「我們的網格是同心環,已符合 Marchal §2.3 給策略一的有利條件」。**那是錯的**,
量了就知道 **[實測]**:

| 邊與局部纖維(圓周)方向的夾角 | 佔比 |
|---|---|
| 0–15°(沿纖維) | 34.0% |
| 75–90°(橫向/徑向) | 13.5% |
| **15–75°(對角線,兩者皆非)** | **51.9%** |

中位夾角 43.7°。這是環狀網格把每個四邊形切成兩個三角形的必然結果 —— **對角線比環向邊和
徑向邊加起來還多**。所以論文那句「edges are oriented along the fiber or transverse
direction」我們並不滿足。

**但另一件事是好消息**:裂縫其實**有在跟著纖維走**。同一段拉動,實際被切開的邊:

| | 裂縫實際走的 | 網格可提供的 |
|---|---|---|
| 沿纖維(<15°) | **65.7%** | 34.0% |
| 對角線 | 22.4% | 51.9% |

中位夾角 **7.5°**,而判據**要求**的方向距纖維中位 **12.6°**。也就是說判據想撕出圓周,
而且在偏好上明顯挑中環向邊(65.7% 遠高於可得的 34.0%)。**方向邏輯是對的。**

問題出在剩下那 22.4%:被迫走對角線時,裂尖就換到另一條環上,累積的徑向漂移最終讓它撞上
自己的舊路。

**試過但沒有採用**:`TEAR_RING_KEEP` —— 選下一條邊時懲罰徑向漂移,讓裂縫留在同一條環上。
概念合理,但**證據不支持**:腳本化拉動下 0 / 0.3 / 0.6 給出切開 72 / 65 / 52、
裂縫跨距 13.0 / 11.9 / 1.6,**越開越糟**。而且它針對的失效(§4.27 那 73.7% 轉角阻擋)
**任何 probe 都重現不出來** —— 連把抓取點每 120 步換位置模擬真實拖曳,轉角阻擋仍是 0.0%。
所以預設 0(關閉),旋鈕留著,但**不在沒有證據的情況下開啟**。

> [補充] 真實 session 會出現 73.7% 轉角阻擋而腳本 probe 完全不會,這個落差本身就是線索:
> 差別在**人手會反覆放開、換位置、從不同方向拉**,而 probe 的拉動模式太規律。下次要查這個
> 失效,得先做出能重現它的 probe,否則任何「修正」都無從驗證。

### 4.31 為何 SofaPython3 有 `addPoints` 卻沒有 `addTriangles`

不是設計上的取捨,單純是**沒有人寫那個 binding**。查 SOFA 安裝目錄即可確認:

```
plugins/SofaPython3/include/SofaPython3/Sofa/Core/
    Binding_PointSetTopologyModifier.h     ← 存在,手寫的 pybind11 binding
    (沒有 Binding_TriangleSetTopologyModifier.h)
```

SofaPython3 對**每個**想暴露方法的類別都要**手寫一份 pybind11 binding**。目前只有
`PointSetTopologyModifier` 有(甚至附了範例 `share/SofaPython3/examples/pointSetTopologyModifier.py`),
`TriangleSetTopologyModifier` 沒有。

至於 `site-packages/Sofa/Component/Topology/Container/Dynamic/TriangleSetTopologyModifier.py`
——**那不是 binding**,是自動產生的**工廠說明樁**(內容只有 docstring 與 `autofunction`),
只讓你能 `addObject("TriangleSetTopologyModifier")`,不會暴露任何方法。

> 所以這是**可以補的**:替 `TriangleSetTopologyModifier` 寫一份 binding 並不困難,
> 但那等於改 SofaPython3 本身(或另外做一個提供 binding 的 plugin)。我們選的是
> §4.26 的路 —— 在自己的 plugin 裡放一個 C++ 元件,由 Data 驅動。

### 4.32 ⭐「特別容易整片皺起來然後炸開」——防護有洞,而且**它自己會把防護關掉**

有記錄,而且記得很完整。使用者這次 13.6 秒的紀錄:

```
t=6.7   stretch    1.60   |coord|  6.89   speed    5.4    ← 健康
t=7.4   stretch  248.34   |coord| 29.01   speed  352.4    ← 一個取樣間隔內爆掉
峰值    stretch 4948.82   |coord|143.99   speed 7195.3
rewinds 總共 6 次          位移夾限最多只擋到 15 個節點(共約 2200)
網格退化率一路到 41% / 64% / 74% / 97%
```

**速度峰值 7195,而 `MAX_SPEED` 是 25。** 夾限完全沒作用 —— 這不合理,除非**夾限根本沒被執行**。

**成因**:`onAnimateEndEvent` 的第一道防護長這樣:

```python
if (not finite or runaway) and (last_good is None or len(last_good) == len(P0)):
    self._rewind()
    return          # ← 這個 return 會跳過下面「所有」的夾限
```

兩個洞:

1. **`last_good is None` 時條件成立** → 呼叫 `_rewind()`,但它第一行就 `if last_good is None: return`
   **什麼也沒做** → 然後外層 `return`,**把速度夾限、應變夾限、抗塌陷、最終位移保護全部跳過**。
   偵測到失控,結果是「什麼都不做,而且連日常防護也一併關閉」。
2. **長度不符時整段不執行** → 失控被偵測到卻被**默默忽略**。而網格一旦退化就**沒有任何幀夠健康
   可以被快取**,下一次分裂又改變頂點數,於是快照長度永遠對不上 —— **防護從此永久失效**。

這就是為什麼 stretch 衝到 4948、rewinds 卻只有 6 次。

**修正**:失控但**無法回滾**時,不再放著不管,改為**就地圍堵** ——
把速度歸零、用 `STRAIN_PANIC_ITERS`(60 次)把超伸的邊硬拉回來,然後**繼續往下跑正常夾限**
(不再 early return)。

實測(刻意用 3 倍猛的拉動,並在中途把快照銷毀來重現該情境):

| | 峰值 stretch | 峰值速度 |
|---|---|---|
| 圍堵關閉 | 17.7 | 25.9 |
| **圍堵開啟** | **9.8** | **25.8** |

更關鍵的是**速度回到 25.8**(上限 25)——對照使用者 session 的 **7195**,正是那條
early-return 造成的。一般情況無回歸(裂口 8.34、抬升 8.94、退化 0.2%、應力回歸全過)。

> [補充] `[Contain]` 訊息會印出當下的頂點數與快照長度,所以下次再發生時,黑盒與主控台
> 會直接說明是「回滾成功」還是「只能就地圍堵」。

### 4.33 ⭐「整個 mesh 都在亂抖」——每次分裂都把兩道防護關掉

使用者回報上一版變成整片亂抖。追下去發現 `_tear_reinit()`(**每次分裂**都會執行)裡有兩行:

```python
self.last_good = self.last_good_rest = None    # ← 丟掉回滾快照
self.prev_pos = None                            # ← 解除每步位移夾限
```

也就是說**每前進一格,兩道防護就被關掉一次**,而撕裂進行中分裂非常頻繁。後果:

- **回滾永遠沒有可用快照** —— 這也解釋了 §4.32 那個「stretch 4948 卻只有 6 次 rewind」:
  我在 `_split_vertex` 裡辛苦把快照長大,結果緊接著呼叫的 `_tear_reinit` 又把它設成 None。
- **位移夾限經常沒作用** —— 實測單步節點位移最大 **1.053**,而 `DISP_CLAMP` 是 **0.5**。
  一半的步數守衛是關的,節點想跳多遠就跳多遠,那就是「亂抖」。

**修正 1**:兩者改為**跟著網格長大**,只有在長度真的對不上時才丟棄;`prev_pos` 也在
`_split_vertex` 裡一併補上複製點。

**修正 2**(修正 1 暴露出來的):應變 panic 原本在階段 (0),**跑在階段 (2) 的應變夾限之前** ——
而夾限存在的目的正是把超伸的邊拉回來。分裂後短暫的超伸(完全正常)因此被判定為爆炸而觸發
回滾;快照一旦真的可用,就變成 **47% 的步數都在回滾**。改為在夾限跑完之後才判定
(`_strain_panic_check`)——**夾限能修好的就不算爆炸**。

實測(同一段拉動):

| | 單步最大位移 | rewinds | 裂口 | 抬升 |
|---|---|---|---|---|
| 修正前 | **1.053**(夾限 0.5) | 5 | 8.34 | 8.94 |
| 只修正 1 | 0.500 ✅ | **233** ⚠️ | — | — |
| **修正 1 + 2** | **0.500** ✅ | **0** ✅ | **8.01** | **9.00** |

中央拉動:切開 76、抬升 7.69、最大拉伸 **1.50**、退化 **0.3%**,應力回歸全過。

> [補充] 「先偵測爆炸再讓夾限修」與「先讓夾限修再判定是否爆炸」看似順序小事,實際差別是
> 47% 的步數在回滾 vs 0%。**防護的順序和防護本身一樣重要。**

### 4.36 ⭐ 撕不開的原因不是門檻,是我自己加的三道閘門

讀 2165 步的真實紀錄(`diag_last.csv`),**判準 c 的中位數是 392,門檻是 20** ——
84.1% 的步數 c 都超過門檻,p90 是 697,最高 16197。**材料一直在說「該撕了」。**
所以調 σ̄_T 完全沒有意義(§4.35 已證實),擋住撕裂的是三道我自己加的閘門 **[實測]**:

| `tip not loaded` | 15.7% | `TEAR_LOCAL_MIN` = 0.4 |

#### (a) 停滯閘門會被裂痕自己觸發

`self._drive_ref = max(S1, ref × DECAY)` 記住的是**切開之前**的峰值。可是**切開本身就會卸載裂尖**
——那正是撕裂的定義。所以每成功咬一口,下一口立刻被自己判定成「使用者放手了」。
這就是「每次只撕一點點就卡住」的機制。

**修正**:切開之後把 ref 重設成切開後的值(`TEAR_ARREST_REBASE`,預設開)。
閘門仍然抓得到**手真的放開**,但不再抓自己。

#### (b) 轉角限制不是「困難」,是**死結**

紀錄裡有連續 **551 步(11 秒)** c 卡在**完全相同的 392.36**、裂痕凍結在 22 格,

"highly dependent on the original mesh",他們的正式版是**任意方向切 + 重網格化**。
所以這個死結是我們的網格限制造成的,不是物理。

**修正**:連續被轉角擋住 `TEAR_BLOCK_ESCAPE`(預設 8)次而判準仍成立時,**硬轉過去**。
只放行轉角限制;「沒有可用邊」「撞回自己的路徑」是真的拓樸死路,強行通過會重切既有唇邊。

停滯閘門修好之後,退化煞車變成第二大阻礙(探針 25% 的步數),而且它是在
**4–7% 退化**時就踩——離真正會把網格絞碎的 24.8% 還很遠。0.04 → **0.10**。

### 4.37 ⭐ 裂痕為何是圓的:那是網格的對稱性,不是物理

讀 2026-08-25 那次 take(`stress_log_0825_171302_1.jsonl`,581 步)**[實測]**:

- 裂痕 102 格,**65% 的步是 ±1 的頂點編號**。
- `generate_cap.py` 的 `_build_raw()` 是**逐環編號**(`for i in rings: for j in segments: verts.append(...)`),
  所以 **±1 = 同一環上的下一個頂點 = 圓周方向的鄰居**。
- 最長的一段:**37 格,半徑 3.85 ± 0.000,掃過 356°**。另外 12 格在 5.85 ± 0.000、9 格在 6.81 ± 0.000。
- **61% 的裂痕頂點落在這種「半徑完全不變」的連續段上。**

半徑準到小數點後三位都不變的「裂痕」,不是在模擬材料,是在把**網格自己的對稱性**讀回來給我們看。
而且這正是 Dequidt 2013 §4.3 點名的失效模式:只沿現有邊走會讓裂痕
"highly dependent on the original mesh"。

**不是非物理的公式**:判準本身沒有偏好圓周。纖維是同心的(`fiberCenter`),σ̄_L = 2.5 σ̄_T,
所以**沿纖維(圓周)撕反而更難** —— 公式是在反對圓形裂痕的。是網格提供了一條圓形高速公路。

#### 修法:把那條高速公路拆掉(`CAP_MESH=irregular`,已設為預設)

藍雜訊(Poisson-disc)取點 + Delaunay 三角化,再抬到橢球面上。外緣仍然保持精確的圓
(懸韌帶錨定與剝離規則都依賴 r ≥ R)。量測 **[實測]**,兩者刻意調到同一解析度:

| | rings(舊) | irregular(新預設) |
|---|---|---|
| 頂點 / 三角形 | 2156 / 4166 | 2172 / 4198 |
| 平均邊長 | 0.304 ± 0.070 | 0.305 ± 0.066 |
| **共半徑邊(圓形高速公路)** | **33.6%** | **2.3%** |
| 面積變異係數 | 0.34 | **0.29** |
| 最小內角 p1 | 23° | **29°**(更少 sliver) |

也就是說新網格**同時**拿掉了圓形偏好**並且**元素品質更好、條件數更好。

**代價**:同一條探針拉動下,裂痕 179 → 163、tearing 64.7% → 62.0%、抬升 6.20 → 4.60,
拉伸 p99 1.53 → **1.46**(較好)。撕裂量略降但在同一量級。

> **探針測不到這件事**:探針的平滑拉動根本不會走環,兩種網格量到的 co-radial step 都是 0%。
> 唯一有效的證據是**真實 take 的紀錄**和上表的**靜態網格統計**。這已經是探針第三次測不到
> 真實 session 才會出現的行為(前兩次:轉角死結、停滯閘門)。

### 4.41 裂痕和手的耦合鏈,以及它為什麼會歪歪扭扭

**完整的鏈**(這是「裂痕跟拉力的關聯」的正本):

```
滑鼠彈簧 F = 600 x 拖曳距離   (單一節點)
   → 解算器把變形擴散到全網格
   → _field_now(): 每個三角形 F = Ds·Dm⁻¹ → Green 應變 → 平面應力 → σ1, σ2, 方向
   → _tip_stress() 把兩件事分開取:
        方向 ← 裂尖自己的元素(實測與「裂尖→手」夾角 0.7–14.5°)   ← 這條真的跟著手
        大小 ← 全網格 1/(1+d²/λ²) 加權的 top-8,λ = TEAR_REACH = 3.0
                 再乘 TEAR_TIP_GAIN,再乘 LEFM √(a/a₀)
   → _argmax_c(): 在裂尖的鄰邊裡挑 c = σ_u/σ̄_u 最大的
        σ_u  = σ1cos²ψ + σ2sin²ψ                    (Dequidt Eq.3)
        σ̄_u = σ̄_T + (σ̄_L−σ̄_T)(1−fold/90)^α        (Eq.4,同心纖維)
   → 航向用 TEAR_DIR_INERTIA = 0.6 平滑,轉角上限 100°(有 §4.36 的脫困)
```

**方向是真的跟著手的**(0.7–14.5°)。**大小不是**——它是全網格的距離加權平均,
所以在遠處拉一樣會驅動裂痕。這就是「沒有拉到哪撕到哪」剩下的那一半原因。

**要靠拉扯把裂痕帶成一圈,這條鏈本身是夠的**:真實 CCC 就是靠術者**重新抓取、切向拉**,
讓裂尖的主應力方向沿著圓周轉。方向既然來自裂尖的應力張量,那就是可以做到的——
**不需要任何寫死繞圈的規則**(而且 §4.37 已證實舊網格的「圓」是網格對稱性,不是規則)。

**歪歪扭扭是「只沿現有邊走」的固有代價 [實測]**:新網格上裂痕的平均轉折角 **65°**(p90 155°)。
把 `TEAR_DIR_INERTIA` 從 0.6 拉到 0.85 可以降到 48°,但撕裂量腰斬(211 → 124)、抬升 5.12 → 3.42,
**不划算**。舊網格看起來平滑只是因為它在騎環。真正的解法是論文的正式版:
**任意方向切 + 重網格化**(Dequidt 2013 §4.3),我們還沒做。

### 4.43 ⭐ 「SOFA 都會這樣亂抖嗎?」不會 —— 是我們的 k/m/dt 加上自己的夾子

#### 為什麼會抖(兩層原因)

**第一層:網格解析不了自己的振動。**
`EDGE_STIFFNESS = 2500`、`massDensity = 1` → ω = √(k/m) = **50 rad/s**,週期 0.126 s,
在 `dt = 0.02` 下只有 **6.3 步一個週期**。隱式尤拉在這裡是**無條件穩定**的,
但**穩定不等於平滑**:任何擾動(一次撕裂切開、一次脫黏、手抖一下)都會以接近步進頻率振盪,
看起來就是嗡嗡抖。要看起來平滑,一個週期大概要 20 步以上。

**第二層(更嚴重):我們自己的安全夾在製造抖動。**
量測同一條抖動拉動 900 步 **[實測]**:

```
位移夾 (DISP_CLAMP) 觸發 14401 次  ->  900 步裡每一步平均把 16 個節點瞬移回去
速度夾              觸發  3525 次
失控回捲               29 次
```

每一次夾都是一次**非物理的瞬間位移**。觸發到這個密度時,它已經不是安全網,
而是**動力學的一部分**。

#### 修法:提高 `rayleighStiffness`(0.2 → 1.0,已設為預設)

Rayleigh 剛性阻尼專打**高頻模態** —— 正好就是網格解析不了的那些 —— 而不像全域黏滯阻尼
那樣把整體動作也拖慢。同一條拉動,連跑兩次結果**位元完全相同** **[實測]**:

| rayleighStiffness | 0.2(舊) | **1.0(新)** | 1.5 | 2.0 |
|---|---|---|---|---|
| 位移夾觸發 | 14401 | **8011** | 10249 | 507 |
| 速度夾觸發 | 3525 | **1755** | 2261 | 122 |
| **失控回捲** | **29** | **1** | 2 | **500** ❌ |
| 裂痕長度 | 111 | **144** | 234 | 203 |
| 最大抬升 | 3.62 | **6.57** | **10.63** | 1.15 ❌ |
| 退化元素 | — | **1.9%** | 5.1% | 2.7% |

**抖動減半、回捲從 29 降到 1,而且撕得更長、掀得更高** —— 因為解算器把預算花在拉扯上,
不再花在它根本表示不了的模態上。

- **不要調到 2.0**:實測那裡整個崩潰成 500 次回捲並凍結(速度 p99 = 0.0、抬升 1.15)。
- **1.5 撕得更多**(234 格、抬升 10.63)但緊鄰那道懸崖,退化元素 5.1%。所以**出貨值是 1.0**。

#### 其他槓桿實測結果

- **`CAP_MOUSE_STIFF` 600 → 200**:夾子幾乎歸零(14401 → 21),但**撕裂也一起死**
  (裂痕 111 → 72)。是那股大力同時在驅動撕裂**和**造成夾子觸發。
- **`CAP_DISP_CLAMP` 0.5 → 1.0**:夾子少了,但抬升 6.57 → 2.62。不划算。
- **`CAP_DT` 0.02 → 0.01**:探針量到夾子暴增,但那是**探針假象**
  (它按步數而非時間移動目標,縮小 dt 等於加倍拉速),**這條沒有被有效量測到**。

所以「要調什麼參數」的答案:**`CAP_RAYLEIGH_K`,已經幫你調好了**。
想更軟更好撕可以試 `CAP_RAYLEIGH_K=1.5`,但退化元素會到 5.1%,而 2.0 會炸。

### 4.44 ⭐⭐ 「外圈超容易掉」的真相:懸韌帶根本沒裝上 —— 一個 launcher 的環境變數洩漏

使用者的物理直覺是對的:外圈應該被懸韌帶固定,滑鼠拉力不可能把整圈扯下來,
內部應該遠早於外圈先撕開。**現在確認:那次跑的時候外圈真的沒有任何錨定。**

`last_run.log` 裡**完全沒有 `[Zonules] rim anchored:` 這一行**,而 tear 模式的預設是要印的。
原因在 `run_cap.ps1`:

```powershell
if ($FreeRim) { $env:CAP_FIX_RIM = "0" }        # <- 全檔唯一沒有 else 的一行
if ($Paper)   { ... } else { ... }              # 其他每一個都有
```

PowerShell 的 `$env:` **在整個 session 內持續存在**。所以只要在那個終端機視窗裡跑過**一次**
`-FreeRim`(§4.19 曾建議、§4.34 已撤回),`CAP_FIX_RIM=0` 就**留在那個 shell 裡**,
之後同一視窗的**每一次**執行都在沒有懸韌帶的情況下跑,而且**log 裡什麼都不會說**。

**代價量測 [實測]**(同一條抖動拉動):

| | 外圈 free(實際跑的) | 外圈錨定(應有的預設) |
|---|---|---|
| 速度夾觸發 | **7899** | 1755 |
| **位移夾觸發** | **35020**(每步 39 個節點被瞬移) | **8011** |
| 最差邊拉伸 | **8.17**(22 條 >3x) | 3.93(2 條) |
| 拉伸 p99.9 | 3.53 | **1.96** |
| 退化元素 | 5.0% | **1.9%** |
| 裂痕長度 | 126 | **144** |

沒有懸韌帶時位移夾多 4.4 倍、過度拉伸的邊多 11 倍,**而且撕得更少**。
截圖裡的尖刺與整片被拖走,就是這個。

**heatmap 沒有錯,是我沒有把兩個欄位合起來看。** 那次紀錄其實已經把真相寫出來了:

```
glued 2172 -> 2080     只釋放 92 點,黏著幾乎完好 -> 並不是「剝離」把膜扯走的
maxcoord max 14.04     但網格伸到半徑 14,而水晶體半徑只有 6.89
```

黏著完好卻伸到 14,只有一個解釋:**膜是被「拉長成尖刺」,不是被「剝下來」**。
黏著是 `RestShapeSpringsForceField`(k=120 的彈簧)不是硬約束,力夠大時它會無限拉長而不「斷開」。

#### 修法

1. `run_cap.ps1` 補上 `else { Remove-Item Env:CAP_FIX_RIM }`。
2. **外圈狀態一律印出來**,包括「沒有錨定」的情形。以前那是靜默的,所以一個殘留的環境變數
   可以讓每一次執行都少掉懸韌帶而沒有任何跡象。這種**看起來像物理 bug 但其實不是**的狀況,
   必須在 log 裡自己講出來。

> **給使用者的立即動作**:如果你的終端機視窗曾經跑過 `-FreeRim`,**開一個新的 PowerShell 視窗**
> (或執行 `Remove-Item Env:CAP_FIX_RIM`)。修正後的 launcher 會自動處理,
> 而且啟動時會印出 `[Zonules] rim anchored: 212 nodes ...` 讓你確認。

**關於「內部應該先撕開」**:外圈用的是 `FixedProjectiveConstraint`,那是**剛性約束**,
強度無限大、永遠不會被拉斷。所以只要錨定真的裝上了,**內部必定先撕開**,這是結構上保證的。

## 5. 做不到什麼、為什麼(這是重點)

反覆調參數**到不了**「像真的撕囊那樣拉起一大片、翻摺、停住」。這**不是調參問題,是模型本質**,四個根本原因:

### 5.1 純彈性,沒有塑性(最大主因)
真實囊膜撕開**不可逆**——撕過永久分開、瓣維持折起。本 demo 是彈性:兩片唇被周圍完好的膜與**邊彈簧**拉回,
一放手裂口就縮回。**實測塑性嘗試失敗**:仿 `cap_membrane` 的做法(把靜止形狀 creep 向當前形狀 + 重烤彎曲靜止角)
不但沒幫忙,反而更差 —— 掀起的瓣放手後只保留 **18%**(塑性)vs **45%**(純彈性)。根因:**邊彈簧一直把瓣拉平**,
而只 creep FEM/彎曲的靜止態贏不過邊彈簧;若連邊彈簧的靜止長也 creep → **無界成長 → 爆炸**。且 `fem.reinit()`
會重載**原始**靜止態、把 creep 洗掉。→ 這個彈性 + 邊彈簧的結構天生做不出「形狀停住」。

### 5.2 裂縫被網格邊量化
裂縫只能沿現有邊、一次一格,做不出平滑大弧,也做不出「一撕一大片」的連續感。INRIA 用**沿路徑重網格**
就是為擺脫這點([`ccc_method/2`](../ccc_method/2_topological_remesh.md)、[`reference/8`](../reference/8_inria_implementation_deepread.md))。

### 5.3 粗網格的裂尖沒有應力奇異性
真實裂尖 σ→∞,所以輕輕一拉就裂;線性 FEM 把它抹平,裂尖受力被低估 → 要嘛拉不動、要嘛把門檻壓到很低
(不自然)。`TIP_STRESS_GAIN` 只是補一個人工集中係數,治標。且力**傳不到遠處的裂尖**(§4 的 `dist-to-tip`),
所以必須「抓在裂尖旁、隨裂縫重新夾」——正是臨床要重新抓握的原因,但對操作者不直覺。

### 5.4 軟 ↔ 穩定的矛盾
要裂口張得開就得把膜調軟(YOUNG 500 時 max-gap 開到 ~1.5),但一軟、手一用力,三角形就塌陷/翻面 →
FEM `Null determinant` 爆掉。只能在中間妥協(現用 YOUNG 900 + 面積夾限)。兩個目標在此模型**天生打架**。

## 7. 結論與下一步

- 本 demo 作為**判據示範**是成功的:裂縫確實照 ⊥σ₁ 自動彎成圓、圓片能掀起露洞,且穩定不崩。
- 作為**手感模擬**已達模型天花板:純彈性 + 網格邊量化 + 無裂尖奇異 + 軟↔穩定矛盾,**調參數改不掉**。
- 要真正的「抓住拉一整片翻起來」,需換架構:
  1. **中期**:仿本 repo JS 解耦 demo,把「裂縫路徑(幾何規則)」與「膜物理(只算脫離片 + PBD/塑性凍結)」解耦;沿路徑重網格。
  2. **完整**:走 INRIA 正本 —— 編 `Capsulorhexis.dll` 的 `FiberFractureEngine`(纖維 FEM + 不可逆斷裂 + 路徑重網格),對齊 Comas 2008 / Allard 2009 / Dequidt 2013。

> 先確認方向,再動工;若走完整路線,第一步是讀 [`ccc_method/4`](../ccc_method/4_inria_fiber_fracture.md) 與
> [`reference/8`](../reference/8_inria_implementation_deepread.md) 把引擎需要的元件/判據/資料流盤清楚。
