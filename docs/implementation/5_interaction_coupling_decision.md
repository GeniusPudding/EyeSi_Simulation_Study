## 0. 實測現象(本 repo 的實驗記錄,非論文)

`Capsulorhexis/scenes/cap_membrane.py` 用 SOFA 的滑鼠抓取(`AttachBodyButtonSetting`)拉扯囊膜三角網格,穩定觀察到兩種死法:

| 死法 | 機制 | 現象 |
|---|---|---|
| **A. 共線** | 三角形被拉成一直線,面積 → 0 | `Null determinant in computeStrainDisplacementLocal` 洗版 → NaN → 幾何消失 |
| **B. 翻面** | 三角形翻過去,co-rotational 抽出的 R 錯誤 | 力指向錯方向 → 正回饋 → 座標衝到 1e11~1e150(有限但巨大,`isfinite()` 抓不到)→ 無聲飛出畫面 |

**實測數據**(基準版 `9cda975`,一次約 41500 秒的長時間操作):
- 全場 40746 筆應力報告中,僅 53 筆(**0.13%**)進入爆炸態;`degenerateTris` 最高 183/4166。
- 但 47 次 `[Runaway]` 事件**只有 4 種相異的 max 值**,最後 12 次全部是 `855.0` → **確定性重演**,即「倒帶 → 重演 → 再爆」的無限迴圈,這就是使用者看到的「閃動」。

換 `TriangularFEMForceFieldOptim` **只消掉死法 A**(它內部守住了 `1/area` 的奇異點),**死法 B 照舊**(實測 areaRatio 仍達 1e5、座標 1e11)。

## 1. FEM 力學式裡的兩個奇異點

> ⚠️ **先讀 §6 再讀本節。** 本節原本把這兩個奇異點當成「爆炸的根源」,**後續實測顯示這個歸因過強**:
> 換成完全沒有這兩個奇異點的 mass-spring 之後**照樣爆**,而且在**完全沒有互動**的最小場景也會爆。
> 本節描述的機制**是真的**(它們確實是 FEM 的失效模式),但**不是我們爆炸的主因**。詳見 §6。

co-rotational 三角形的元素力(機制詳見 `engines/7` §E):

```
f_e = R · K_e · (Rᵀ·x − x₀)

其中 K_e 由應變位移矩陣 B 組成,而 B 含  1/(2A)     ← A = 三角形面積
     R 由當前形狀抽出(極分解 F=R·U,或邊向量 Gram-Schmidt)
```

- `1/(2A)`:A → 0 時發散 → **死法 A**。
- `R`:三角形翻面(det F < 0)時抽出的 R 是錯的 → f_e 反向 → 越推越翻 → **死法 B**。

對照彈簧:

```
f = k · (‖x_b − x_a‖ − L₀) · 單位向量        ← 只有距離;無 A、無 R
```

彈簧**在數學上不可能自我放大**(拉長就往回拉),所以 mass-spring 版不會有這兩種死法 —— 代價是失去連續體應力場的物理基礎。

> **關鍵**:死法 A、B 都不是「參數沒調好」,而是需要**一個足夠大的外力把三角形推到那個狀態**。我們的外力來源正是問題所在。

## 2. 我們的外力來源:無上限的懲罰彈簧

`AttachBodyButtonSetting`(SOFA 的 Shift+拖曳抓取)在抓點與游標之間掛一根**懲罰彈簧**:

```
F = MOUSE_STIFFNESS × (游標離抓點的距離)      ← 距離沒有上限 ⇒ 力沒有上限
```

拖得快或遠 → 單一時間步注入巨大衝量 → 三角形被推到共線或翻面。**任何降低剛度的調參都只是把門檻往後推**,因為距離項本身無界。

實測佐證:本 repo 曾嘗試三種「事後補救網」(倒帶迴圈偵測 + 阻尼 boost、rest 面積刷新、以局部修復取代整片倒帶),**全部比基準版更糟**(最嚴重一次 4165/4166 三角形毀損)。原因是這些網都在 `onAnimateEndEvent` 執行,而錯誤誕生於 **solve 之內**,永遠慢一步。

## 3. INRIA 怎麼做(依 `reference/8` 的一手論文深讀)

**他們用同樣的 co-rotational**,而且用在同一批對象上:

| 項目 | 內容 | 出處層級 |
|---|---|---|
| 囊膜三角、水晶體四面體、IOL 殼 | **co-rotational** | Marchal 2009 / Dequidt 2013 原文 |
| 時間積分 | 隱式,**dt = 0.01 s** | Dequidt 2013 原文 |
| 線性解 | matrix-free GPU-CG(K 從不組裝) | Marchal 2009 / Dequidt 2013 原文 |
| **器械 ↔ 組織的耦合** | **接觸回應:Saupin _contact-warping_**(接觸力分配、含摩擦,為 co-rotational 設計) | Dequidt 2013 §5.2.3(Saupin [24]);shell FEM 為 Dequidt 自家、非 Comas |
| **器械本身** | **IR 光學追蹤的剛體**(6 台相機、每器械 4 反光標記、VRPN);Dequidt **明確否決力回饋觸覺筆** | Dequidt 2013 原文 |
| 條件數 | 非同步預條件子(軟硬不均組織收斂慢的解法) | **Courtecuisse 2010**(非 Dequidt) |

**差異:INRIA 不用「一根無上限的橡皮筋去抓住一個節點」。** 他們的器械是**位置由追蹤決定的
剛體**,組織透過**接觸回應**與之互動。

> ⚠️ **原文校正(2026,回 Dequidt 2013 原文核對)。** 本節原本把 INRIA 的接觸寫成「**約束式的
> 摩擦接觸 / 約束求解器算出恰好的有界力**」——**這是過度詮釋,原文沒有這樣說**。Dequidt 2013 §5.2.3
> 實際用的是 **Saupin *contact-warping*(接觸力分配法,為 co-rotational 設計、含摩擦)**,原文描述是
> 「把接觸的法向力分配成三節點的力與力矩」(force/torque distribution),**全篇沒有 LCP / Signorini /
> Lagrange / 約束求解器 / FreeMotionAnimationLoop**。而且論文把**穩定性**歸給:**隱式積分**(§3.2.1
> 「stable simulation even when subjected to challenging interactions」)+ **對硬又輕的 IOL 改用直接
> 解算器**(§5.2.4「high stiffness and low mass … a direct sparse solver … more stable」)+ **dt=0.01**
> —— **不是「有界接觸力」**。所以「INRIA 靠約束式接觸避免爆炸」這條推論,原文不支持;§6 的實測也另從
> 反面推翻它(見下)。詳細原文核對見 [`reference/8`](../reference/8_inria_implementation_deepread.md)。

## 5. 我們還缺什麼(三件事,彼此獨立)

### 5.1 約束式接觸(~~最高優先~~ **已被 §6 推翻,見下**)

> ⚠️ **先讀 §6。** 本節原本主張「約束式接觸是針對爆炸根源、最該先做的改動」。**這個推論已被 §6 的
> 實測推翻**(運動學腳本拉扯——最極致的有界耦合——照樣爆),也與原文不符(§3 校正:INRIA 用的是
> contact-warping、穩定性來自隱式+直接解算器)。保留本節僅為記錄推理過程;**不要**為了穩定去做它。

把「懲罰彈簧抓取」換成**約束式耦合**:`FreeMotionAnimationLoop` + 約束求解器(LCP / `GenericConstraintSolver`)+ 膜上的 `ConstraintCorrection`。

- **解決什麼**:拉力有界 ⇒ 元素不被逼到共線/翻面 ⇒ **不爆** ⇒ 不需要倒帶網 ⇒ **閃動消失、變形不再被還原**。
- **副作用**:換的是求解器管線,碰撞回應、黏著彈簧、阻尼都要相容,需要自己的整合輪次。
- **附帶好處**:不爆之後 **co-rotational FEM 可以用回來**,連帶拿回連續體應力場。

### 5.2 面內塑性 = 需要自訂 C++ 力場

**現況**:塑性只重烤了**彎曲** rest(折痕會定形),**面內從未實作過**(FEM 版與 mass-spring 版皆然)。

**為何 Python 做不到**:`MeshSpringForceField` 的每根彈簧 rest 長度存在 C++ 內部陣列,**未公開成 Data 欄位**,Python 只能呼叫 `reinit()` ——那是「把全部邊的 rest 一次重設成當前長度」的大槌,**包含已經爆掉的區域**,等於無屈服的塑性流動(實測:areaRatio 衝到 1e4~1e5)。

**要做對需要**:一個逐邊維護「塑性 rest 長度 + 屈服門檻 + 累積上限」的力場。這在 SOFA 只能寫成 **C++ 元件**。

> [補充] INRIA 也是這樣做的:`reference/8` §7 的元件對映([推論] 標記)顯示 Dequidt 系統含**自訂 shell ForceField**(IOL)、**自訂 FractureComponent**(argmax c 準則)、以及囊膜的**自訂纖維各向異性**。寫自訂 C++ 力場在這個領域是常態,不是偏門。本 repo 已具備 plugin 建置流程(`Capsulorhexis/`、`scripts/setup.ps1`)。

### 5.3 器械表示(研究用途可延後)

INRIA 用 IR 追蹤的實體器械。研究/教學 demo 用滑鼠或腳本軌跡即可,**不是穩定性的根因**,可延後。

## 6. ⚠️ 更正:上述「約束式接觸能解決爆炸」的推論,已被實測推翻

§5.1 原本建議「先做約束式接觸,它是唯一針對爆炸根源的改動」。**後續實測證明這個推論是錯的**,以下是量測結果(本 repo 實驗記錄,以可重現的**運動學腳本拉扯**在 headless batch 模式取得,完全不經滑鼠)。

### 6.1 六個假設,逐一排除

| 假設 | 測法 | 結果 |
|---|---|---|
| **約束式接觸能解決** | 同一片膜,只切換 `FreeMotionAnimationLoop`+LCP vs `DefaultAnimationLoop` | ❌ 尖峰統計**逐位元相同**。無約束時約束管線是忠實 no-op → **它不會解決這個問題** |
| CG 截斷是主因 | 換成精確的 `SparseLDLSolver` | ❌ 仍爆(degen 624),且 FPS 掉到 14 |
| CG 迭代不足 | 30 / 60 / 100 / 300 掃描 | ❌ **非單調**:30 與 300 通過、60 與 100 崩潰 → 臨界穩定,調參是賭博 |
| 鏡片斥力是主因 | `LENS_REPULSION = 0` | ❌ 仍爆(degen 857) |
| 滑鼠懲罰彈簧是主因 | 純運動學腳本拉扯(無滑鼠) | ❌ 照樣爆 |
| 黏著瞬間斷裂是主因 | 逐點勁度 25 步淡出 + 每步最多釋放 40 點 | ❌ 無改善,部分更糟(rawMax 3.8e8 → 1.7e70) |

### 6.2 唯一確認有效、但不充分的因素

**`massDensity` 1 → 10**。節點質量 ≈0.084 而邊彈簧 k=2500,自然頻率 ω=√(k/m)≈172 rad/s → 週期 0.036 s,在 dt=0.02 下**一個週期只有 1.8 步**,嚴重欠採樣。隔離掃描:m=1→24.3×、m=3→5.1×、m=5→2.8×、m=8→1.59×(首個無尖峰)、m=10→1.03×。完整場景中把 degen 峰值從 3188 壓到 282,**但撐不過所有拉法**,且伴隨手感變重。

### 6.2b FEM vs mass-spring:換材料模型沒有換到任何穩定度

同樣的運動學腳本拉扯,其餘完全相同(2026-07-23 實測):

| 拉扯 | mass-spring | `TriangularFEMForceFieldOptim` | FEMOptim + massDensity 10 |
|---|---|---|---|
| **溫和(T=6.0, move 1.5,0,3 = 場景預設)** | rawMax 1.79e3,degen **0** | rawMax 1.77e3,degen **0** | rawMax 1.76e3,degen **0** |
| 積極(T=2.0, move 4,0,7) | rawMax 8.19e19,degen 4071 | rawMax 1.13e20,degen 3869 | rawMax 1.00e10,degen 3591 |
| 積極(T=1.5, move 5,0,9) | rawMax 4.48e8,degen 3707 | rawMax 9.32e15,degen 4142 | — |

`Null determinant` 出現次數:**全部 0**(FEMOptim 確實消掉了死法 A 的洗版)。

**結論:正常拉扯下兩者一模一樣乾淨;猛拉下兩者都爆、量級相當。** 當初改用 mass-spring 是為了解決爆炸,而**它並沒有解決**。既然穩定度相同,FEM 就是嚴格較優的選擇——它提供撕裂判準要的**真實連續體應力張量**、可引用的 **E/ν 物理參數**,以及通往**纖維各向異性 + `Capsulorhexis` plugin 撕裂模型**的路。**因此已於 2026-07-23 把 `USE_MASS_SPRING` 改回 `False`。**

### 6.2c 真正找到的兇手之一:阻尼器是**顯式**積分的(commit `e466e06`)

上面所有排除測試都沒問到的一件事:`UniformVelocityDampingForceField` **預設不參與隱式矩陣**,等於**顯式**積分。顯式力場只有**條件穩定**,而此處 `c·dt/m` 最高達 **~100** —— 遠超穩定界限,所以它自己就會發散。這解釋了「完全剝離後、idle 狀態仍會爆」以及靜置時的抖動。

修法是把它設成 `implicit=True`(納入隱式系統)。這與 §6.1 的結論一致而非矛盾:**爆炸是多源的**,而這是其中一個真正的、可指名的來源。

> **教訓**:排除法只能排除「你想到要測的東西」。「某個力場其實是顯式的」這一類問題,不會出現在任何參數掃描裡——**要去讀元件的積分方式,而不是只掃參數。**

`e466e06` 同時加入:每步位移夾 + 最終渲染守衛(爆掉的幀到不了螢幕)、應變夾改為逐節點平均修正並移除分離速度分量(消除 2→25→2 的回彈跳動)、脫黏改為 ~5 步逐點勁度淡出、以及每步 `diag_last.csv` 診斷。

### 6.3 最關鍵的對照

一個剝到只剩「膜 + 固定外緣 + 重力」(**無鏡片、無黏著、無抓取**,massDensity 10)的最小場景,**完全穩定**:1000+ 步後靜止在平衡,最大邊拉伸 1.032,零尖峰。

> **結論:膜本身是穩的。不穩定來自疊在它上面的互動與邊界力,而且不是單一來源 —— 沒有任何單一旋鈕能解決。** 彈簧網在 k=2500 / dt=0.02 下處於臨界穩定,多個互動源都能各自把它推翻。

### 6.4 現行建議

1. **基準 = commit `9cda975` + 改回 FEM**(`USE_MASS_SPRING=False`,用 `TriangularFEMForceFieldOptim`;自碰撞維持關閉、相機裁切修正保留)。`9cda975` 的其餘部分是補丁路線的**局部最佳解**——實測多次額外補丁皆更糟——但其中的 mass-spring 選擇已由 §6.2b 推翻。
2. **不要再投資約束式抓取來解爆炸** —— §6.1 已證明無效。(它若有價值,是為了將來的摩擦接觸/器械擬真,不是為了穩定性。)
3. §5.2(自訂 C++ 塑性力場)仍然獨立有效 —— 它解的是「拉開會縮回」,與爆炸無關。
4. 若日後仍要追穩定性,**唯一有方法的路**是從 §6.3 那個穩定的最小場景出發,把鏡片/黏著/抓取**一次加一塊**,每加一塊用 headless harness 量尖峰。但要有心理準備:那三樣正是量測到會破壞穩定的東西。
